# AlphaOx 路径六：确定性 CI 与外部参考数据源详细开发计划

## 0. 计划状态与决策边界

- **状态**：`PROPOSED`，尚未开始实现。
- **目标**：用可公开、固定种子、自有数据证明 Context、Plan、Tool、Result、Evidence 和 Web 状态的可重复性。
- **外部数据边界**：Olist 与 AdventureWorks 只能作为独立 Source Finding；下载、导入、许可核验和清理不能悄悄进入正常 CI 或安装包。
- **前置条件**：路径二、三的契约稳定；路径四/五已经有可注入的 Tool 和本地工作台接口。
- **不授权事项**：不下载未经批准的外部数据，不连接真实企业来源，不把第三方完整数据提交 Git、CI artifact、安装包或镜像。

## 1. 交付目标

建立一套无需真实模型、真实数据库或外部服务即可运行的 Golden Questions，验证：

- 两套不同物理 Schema 可以表达同一业务事实。
- Binding、freshness、权限和术语规则被机器契约正确消费。
- 结构化、知识和混合问题有稳定的计划、结果、证据和失败状态。
- 许可、版本和数据传播边界不会被测试便利性绕过。

## 2. 分阶段开发计划

| 阶段 | 交付 | 关键检查 | commit 门 |
| --- | --- | --- | --- |
| 6.0 Fixture 规范 | 固定种子、数据目录、Schema 版本和生成器约束 | 不含真实行、凭据、飞书内容和不可审计随机值 | 规范与生成器提交 |
| 6.1 双 Schema | 两套物理表结构、同一业务事实和 Snapshot/Binding | 计划可迁移但物理引用不同；结构指纹和映射可解释 | fixture 测试通过后提交 |
| 6.2 知识包 | 术语、数据字典、退款政策、促销日历、freshness 和权限文档 | 来源、版本、生效期和冲突规则闭合 | Context fixture 检查后提交 |
| 6.3 Golden Questions | 结构化、知识、混合、澄清、空、阻断和过期问题 | 预期 Plan/Result/Evidence/状态均版本化 | Golden tests 通过后提交 |
| 6.4 外部 Source Finding | Olist/AdventureWorks 来源、版本、许可证、适用边界记录 | 只记录核验结果，不把完整数据带入 CI/镜像 | 独立来源门后提交 |
| 6.5 CI 集成 | 生成、校验、契约测试、差异检查和敏感扫描 | 固定输出、失败可读、无外部联网依赖 | 根级检查后提交 |
| 6.6 Pass 集成 | 对抗复核、许可证复核、回滚和人类 Gate | 所有外部状态分层记录，不能宣称生产数据通过 | Gate 后合入 `pass-06` |

## 3. Fixture 设计

建议业务域保持最小：订单、订单行、退款、区域、日期和促销。两套 Schema 可以分别采用：

- 订单事实集中表 + 维度表。
- 订单、订单行和退款拆分表 + 不同物理命名。

两套 Schema 必须通过不同的 Snapshot、Binding 和 ExecutionSpec 表达同一业务事实，不共享物理名称假设。所有数据使用固定 seed、稳定排序和公开可分发文本。

## 4. Golden Question 类型

- 结构化：按区域统计订单额、退款率和时间窗口。
- 知识：查询退款政策、指标定义和促销规则，并返回来源和生效期。
- 混合：结合结构化结果与政策文档，明确区分观察值和解释。
- 澄清：缺少时间范围、区域、指标口径或比较基准。
- 阻断：未发布 Binding、无权字段、过期 Snapshot、不支持关系或超预算。
- 结果边界：零行、null、重复行、截断、部分来源失败和证据不可封装。

每个问题固定保存问题引用、Context Pack 版本、预期 Analysis Plan、Query Plan、状态、Result 摘要、Evidence 引用和允许的警告；不保存完整模型提示词或原始完整数据行。

## 5. 外部参考数据与许可

- Olist：只记录来源、版本、许可证和是否适合作为本地开发参考；默认不进入 CI、安装包或商业镜像。
- AdventureWorks：只在独立实现门确认具体版本、许可和下载方式后使用；不得仅凭名称推断当前版本或传播许可。
- 下载、校验、导入、转换和清理必须是隔离流程，使用明确目录、dry-run 和 readback。
- Source Finding 不能替代供应链、许可证或生产数据审查，也不能证明 AlphaOx 已连接这些来源。

## 6. 验收与失败矩阵

| 场景 | 预期结果 |
| --- | --- |
| seed、Schema 或 fixture 版本改变 | Golden 结果差异可读，CI 失败，不自动更新基线 |
| 两套物理 Schema 无法映射同一事实 | `blocked`，记录缺失 Binding，不改写业务口径 |
| Context 文档缺版本/来源/生效期 | fixture 校验失败 |
| Golden 结果含任意 SQL、凭据或完整提示词 | CI 失败并阻断提交 |
| 外部数据下载失败/许可未知 | Source Finding `BLOCKED`，不影响无外部依赖的确定性 CI |
| 结果或证据状态变化 | 必须由人工审查 diff，不能直接更新快照 |
| 运行环境联网或读取个人数据 | 测试失败；CI 只使用项目自有 fixture |

## 7. 测试与运行约束

- CI 默认离线、固定种子、无真实模型、无真实数据库和无外部写回。
- 代码变更后运行适用包级测试和根级 `npm run check`；不执行未获授权的全量发布流程。
- 对抗审查关注随机性、时区、locale 排序、Schema 漂移、许可证误报、敏感文件误收集和 Golden 基线漂移。
- 本路径没有独立 Browser 视觉门；若修改 Web 展示契约，必须回到路径五的完整 Browser 清单。

## 8. 分支、commit 与回滚

- 从 `main` 使用 `codex/alphaox/pass-06`；切片使用 `codex/alphaox/pass-06-<slice>`。
- 每个阶段提交生成器、fixture、文档和测试的明确路径；禁止提交外部完整数据和未审查 artifact。
- 回滚为删除/回退自有 fixture 版本、Golden 基线或生成器 commit；不删除外部来源缓存，外部缓存必须由独立流程按范围清理。
- 任何许可证结论、公开分发、镜像打包或外部下载都需要单独确认和实际 readback。

## 9. 人类 Decision Gate

实现前必须确认两套 Schema 的业务范围、Golden Question 清单、外部 Source Finding 的证据等级、许可/版本核验方式和 CI 是否严格离线。未确认前只维护本计划，不建立外部数据依赖。
