## 1. 目标、事实与成功标准

### 1.1 真实目标

AlphaOx 是一个可通过 Docker 部署给公司内部多用户使用的通用分析 Agent。
用户在 Web 工作台用自然语言提问，Agent 在受授权的数据库、API、文件和
企业知识资源上发现上下文，提出机器可验证的分析计划，由确定性执行层取得
数据和文字证据，最后输出图表、表格、解释和可持续保存的报告。

“通用”指协议、权限边界、计划、证据和扩展方式可以适配不同物理 Schema，
不是承诺任何数据库无需审核即可得到正确的业务口径。业务含义、指标定义、
关系和生效时间必须通过版本化的适配资产表达，并允许人类审核。

### 1.2 已核实事实

- 上游仓库是 `earendil-works/pi`，当前 AlphaOx 远程为
  `https://github.com/archerthegoat/alphaox.git`，上游保留为 `upstream`。
- Pi monorepo 已有 `agent`、`ai`、`server`、`protocol` 和 session backend
  等包；当前仓库没有 AlphaOx 的 Docker 服务、Web 工作台或语义分析实现。
- Pi Agent Core 提供事件、上下文转换、工具调用、取消和订阅等 Agent 运行
  能力，但不提供 AlphaOx 所需的企业身份、数据源权限、语义资产发布、查询
  编译、证据最小化、报告所有权或多租户隔离。
- Pi 自身明确没有内置的文件系统、进程、网络和凭据权限系统；这些权限
  必须由产品宿主和部署边界负责。
- `pi-server` 与 protocol 是实验性、传输层相关能力，不能直接当作完整的
  AlphaOx 产品服务契约。
- Olist 与 AdventureWorks 只作为后续 Source Finding 研究对象；当前不下载
  外部数据，也不把完整数据放进仓库或镜像。

## 2. 决策与理由

### D1：Fork Pi，保留上游边界

**决定**：AlphaOx 直接基于 Pi 源码二次开发，`origin` 指向
`archerthegoat/alphaox`，`upstream` 指向 `earendil-works/pi`。AlphaOx 产品
代码集中在两个新包中，尽量不把公司业务规则写入上游核心包。

**理由**：需要复用 Pi Agent 的事件和运行时能力，又要让上游同步、冲突审查
和回滚可执行。把产品边界放在宿主层，可以避免把通用 Agent Core 变成不可
维护的业务分支。

### D2：两个产品包，职责分明

- `semantic-agent`：服务端 Agent 宿主、身份注入、权限策略、上下文发现、
  连接器、计划契约、确定性编译与执行、证据、会话、记忆、报告、Trace、
  HTTP JSON/SSE API。
- `semantic-web`：对话工作台、结果块、图表、表格、报告、来源和 Trace 的
  可访问呈现；前端不执行模型输出的任意代码。

Pi 的 `agent`、`ai`、`protocol` 和 `server` 保持上游可同步的依赖方向。

### D3：Pi Agent Core 只负责 Agent 运行时

**Pi 负责**：模型调用适配、Agent 状态、事件、上下文转换、受控工具调用、
取消和生命周期。

**AlphaOx 负责**：用户和组织身份、会话所有权、权限前置、Context Pack、
Analysis Plan、Query Plan、计划编译、只读执行、结果最小化、证据封装、
报告、审计和服务 API。

这条边界是必要的，因为 Pi 没有产品级数据权限系统；把权限藏在 prompt
中会导致“模型理解了规则”被误当成“系统强制执行了规则”。

### D4：模型提出受约束计划，确定性代码执行

模型只能生成通过 Schema 校验的 `Analysis Plan` 和 `Query Plan`。计划引用
已经发布且已授权的来源、资产、指标、维度、时间范围、过滤器、排序和行数
限制；模型不得直接生成或执行任意 SQL、JavaScript、TypeScript、Shell 或
其他代码。计划编译器负责方言映射、参数化、关系与粒度校验、预算、超时和
取消。

这样仍然保留语言模型在理解问题、澄清和组织分析上的价值，同时把权限、
成本和查询安全放在可测试的机器契约中。

### D5：Context Pack 是可版本化的适配资产，不等于向量库

Context Pack 统一封装结构化上下文、业务术语、文字知识、权限、来源、版本、
生效时间、新鲜度和样例问题。精确字段、结构化关系和别名匹配优先；向量
检索只用于授权后的上下文发现，不作为指标定义、权限判断或数值查询的唯一
权威来源。

每个物理数据源不需要被写成一个不可复用的 Agent；它需要提供可验证的
`Source Snapshot` 与 `Source Binding`。Binding 可以由 Agent 起草，但发布
关键指标和口径必须有人类审核。

### D6：PostgreSQL 是生产控制面，开发允许本地替代

正式多用户运行以 PostgreSQL 保存用户、组织、角色、会话、记忆、报告、审计、
上下文资产和运行状态。SQLite 只允许测试或单机实验，不作为生产多用户的
权威状态库。首版不强制 Redis、向量数据库和对象存储；需要时通过独立契约
增加，不把可选设施伪装成当前依赖。

### D7：HTTP JSON + SSE 是首版产品 API

`semantic-agent` 对外提供版本化 HTTP JSON API；长任务和 Agent 事件通过
SSE 推送，客户端必须能在断线后按 `run_id` 重新读取状态或重新订阅。Pi 的
实验性 transport 代码可以作为参考或内部适配，但不直接等同于 AlphaOx 的
登录、权限、状态和报告接口。

### D8：Docker Compose 作为开发/演示边界

首版开发和演示由 `semantic-web`、`semantic-agent`、`postgres` 组成；可选
demo-source 只在显式 profile 中启用。真实企业连接、生产 OIDC、密钥、原始
数据和外部写回不进入本路径。容器不是唯一权限层；产品策略仍需在服务端
确定性执行。

## 3. 拒绝的方案与取舍

| 方案 | 处理 | 主要理由 |
| --- | --- | --- |
| 把 Pi 的 `pi-server` 直接作为产品后端 | 拒绝 | 它是实验性传输/监听能力，不含 AlphaOx 的身份、数据权限和证据契约。 |
| 让模型直接生成 SQL 并执行 | 拒绝 | 无法可靠强制表级权限、成本、只读、隐私和审计；提示词不是安全边界。 |
| 每个数据集做一个固化的“电商 Agent” | 拒绝 | 不能复用；适配资产应与 Agent 内核分离，使用 Snapshot/Binding/Context Pack。 |
| 首版强制向量库、Redis、对象存储 | 拒绝 | 增加运维和失败面，不能证明首版分析闭环；延后到有明确契约的路径。 |
| 生产控制面使用 SQLite | 拒绝 | 多用户并发、迁移、锁和恢复边界不适合作为正式权威状态。 |
| 把 Olist/AdventureWorks 完整数据提交 Git 或打进镜像 | 拒绝 | 数据版本、许可、体积和传播边界需要单独核验；CI 应使用自有确定性小数据。 |
| 首版接入真实企业数据库 | 拒绝 | 身份、网络、密钥、数据新鲜度和误用责任尚未通过独立决策门。 |
| 先做复杂多 Agent 编排 | 延后 | 先冻结单 Agent 的计划、执行和证据契约；多 Agent 会放大状态与权限复杂度。 |

## 4. 契约与边界

### 4.1 组件边界

```text
semantic-web
  └─ HTTP JSON / SSE
       └─ semantic-agent
            ├─ Identity Adapter + Policy Engine
            ├─ Pi Agent Host
            ├─ Context Resolver
            ├─ Plan Validator / Compiler
            ├─ Read-only Executor
            ├─ Evidence + Report Builder
            └─ PostgreSQL Control Plane
                 └─ Source Connector（运行时连接外部来源）
```

浏览器永远不直接连接企业数据源。连接器凭据只在服务端运行时存在，查询
结果经过权限、列裁剪、行限制、脱敏和证据封装后才发送给客户端。

### 4.2 核心对象

| 对象 | 必须表达 | 不负责表达 |
| --- | --- | --- |
| Source Connector | 连接测试、结构发现、能力声明、只读执行、取消、健康检查 | 业务指标真义、用户授权决定 |
| Source Snapshot | Schema、表、字段、类型、键、行数、方言、结构指纹、发现时间、新鲜度 | 永久业务口径 |
| Source Binding | 业务概念到物理字段/关系的映射、粒度、时间口径、版本、生效期、审核状态 | 运行时权限绕过 |
| Context Pack | 结构化上下文、术语、文档、权限、来源、版本、生效时间、新鲜度 | 未授权原始数据 |
| Analysis Plan | 澄清、查询、检索、计算、比较、可视化、报告步骤 | 可任意执行的代码 |
| Query Plan | 发布资产、指标、维度、时间、过滤、排序、限制、预期证据 | 任意 SQL 字符串 |
| Evidence Envelope | 结果摘要、文字证据、来源、版本、`as_of`、新鲜度、权限范围、状态、警告、Trace | 未经裁剪的企业全量数据 |
| Report | 结构化结果块、方法、来源、警告、状态、所有权、版本 | 没有来源的结论 |

### 4.3 状态与终态

所有运行、查询和报告必须显式使用以下终态之一：

- `complete`：计划和证据完整，所有关键步骤满足契约。
- `partial`：部分步骤完成或部分来源可用；必须列出缺失、影响和已完成范围。
- `blocked`：权限、连接、策略、依赖或安全门阻断，不得伪装成空结果。
- `clarification_required`：用户问题缺少会改变口径、范围或权限的必要信息。

中间状态至少包含 `queued`、`planning`、`awaiting_clarification`、`executing`、
`cancelling` 和 `reconnecting`，并带 `run_id`、`trace_id`、用户/组织边界、
策略版本和创建时间。状态不能仅由 HTTP 200 或模型文字判断。

### 4.4 API 最小契约

首版接口草案如下，实际 Schema 在路径二冻结：

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| `POST` | `/api/v1/runs` | 接收问题和显示偏好；服务端注入身份，不信任客户端身份字段。 |
| `GET` | `/api/v1/runs/{run_id}` | 读取当前状态、摘要、警告、来源、`as_of` 和 Trace 指针。 |
| `GET` | `/api/v1/runs/{run_id}/events` | SSE 订阅受授权事件；断线使用 `Last-Event-ID` 或重读状态。 |
| `POST` | `/api/v1/runs/{run_id}/cancel` | 仅运行所有者/授权角色可取消；结果保留取消原因。 |
| `GET` | `/api/v1/reports/{report_id}` | 读取报告及其所有权、证据和版本。 |
| `GET` | `/api/v1/health` | 只暴露非敏感服务健康和依赖状态。 |

事件包含 `event_id`、`run_id`、`trace_id`、`type`、`occurred_at`、`status`、
`payload_version` 和最小必要 payload。原始行、凭据、完整提示词和敏感字段
不得进入普通事件流。

## 5. 权限、隐私、数据新鲜度与所有权

### 5.1 权限顺序

1. 身份适配器从已认证请求或开发身份注入 `user_id`、`org_id`、角色和策略版本。
2. 策略引擎在上下文发现前过滤可见 Source、Binding、Context Pack 和报告。
3. 计划验证器再次检查来源、列、行、时间范围、预算和只读能力。
4. 执行器使用服务端凭据和已授权的连接器，不接受浏览器传入的凭据或 SQL。
5. 结果封装器执行列裁剪、行限制、脱敏、聚合和来源标记。
6. 报告和记忆按用户、组织和共享范围保存；默认不跨用户共享。

拒绝应返回 `blocked`，并给出不泄露资源存在性的安全说明。不能先让模型
看见全量 Schema 再在 UI 上隐藏。

### 5.2 状态所有权

- 用户拥有自己的会话、运行和个人记忆。
- 组织/租户拥有明确发布并共享的 Context Pack、Binding 和报告。
- 管理员可以审计和撤销，但不能因 UI 角色显示而绕过服务端策略。
- 缓存键必须包含组织、用户/共享范围、资产版本和策略版本。
- 删除、撤销和过期需要审计记录；本路径不实现物理清理策略，只冻结边界。

### 5.3 新鲜度

每个 Snapshot、Binding、Context Pack、证据块和报告都要携带发现或查询时间、
来源版本、`as_of`、新鲜度等级和过期规则。过期不等于“没有数据”：

- 可刷新：进入重发现或重查流程。
- 可用但过期：允许输出时标为 `partial` 或 warning，由策略决定。
- 关键指标已过期且禁止使用：`blocked`，不得静默使用旧值。
- 新鲜度未知：视为证据缺口，必须在结果中显式显示。

## 6. 状态 / 失败矩阵

| 场景 | 服务端状态 | 用户可见结果 | 是否重试 | 审计要求 |
| --- | --- | --- | --- | --- |
| 身份缺失或过期 | `blocked` | 登录/身份不可用，不暴露数据详情 | 需重新认证 | 记录拒绝原因和策略版本 |
| 无权访问来源/字段 | `blocked` | 授权不足；不显示隐藏资源的存在性 | 否，除非权限变化 | 记录资源类别，不记录敏感值 |
| 需要业务口径或时间范围 | `clarification_required` | 展示一个最小澄清问题，保留原问题 | 用户确认后继续 | 记录澄清前后计划版本 |
| Snapshot 过期 | `partial` 或 `blocked` | 显示过期时间和影响范围 | 可按策略刷新 | 记录 freshness decision |
| 连接超时 | `partial` 或 `blocked` | 区分无结果与连接失败 | 有限退避，受预算控制 | `error_code`、耗时、重试次数 |
| 查询违反权限/成本/粒度 | `blocked` | 说明计划未通过策略，不展示 SQL | 否，需重规划 | 保存校验失败类别 |
| 某来源失败、其他来源成功 | `partial` | 输出已完成证据和缺失来源 | 有限重试 | 记录每个步骤状态 |
| 模型不可用 | `blocked` 或 `partial` | 已有结果可读；未完成步骤明确缺口 | 受预算控制 | Provider 状态不含密钥 |
| SSE 断线 | 运行状态保留 | 客户端重连并补事件或读快照 | 有界重连 | 记录连接断开，不重复执行查询 |
| 用户取消 | `blocked`（原因 `cancelled`） | 显示已完成和取消边界 | 否，除非用户新建运行 | 记录操作者与取消时间 |
| 结果脱敏失败 | `blocked` | 不发送该结果块 | 否，需人工处理 | 记录策略和字段类别 |
| 报告保存失败 | `partial` | 结果可临时查看，报告未保存 | 可重试保存 | 记录所有权和持久化失败 |

### 6.1 防止“空结果”误判

`zero_rows`、`source_unavailable`、`permission_filtered`、`stale_snapshot` 和
`query_not_run` 必须是不同的结构化原因。前端不得把这些原因都显示为“没有
数据”。同理，模型没有回答不代表查询返回零行。

## 7. 边界情况与对抗问题

- 同义字段同时出现在两个来源：必须要求 Binding 或澄清，不能按字段名猜测。
- 一个指标的分母为空或为零：返回不可计算及影响，不输出伪造百分比。
- 数据源时区和用户时区不同：计划必须显式携带时区和边界语义。
- 订单取消/退款跨日：业务事实与分析时间口径必须由 Binding 定义。
- 多来源相同实体无法对齐：标记不可比，不做静默拼接。
- 结果超过行数、字节数或图表点数预算：聚合、分页或 `partial`，不得超限发送。
- 文字知识与结构化数据冲突：分别展示来源和生效时间，进入澄清或阻断。
- Context Pack 被撤销但旧报告仍存在：旧报告保留原版本引用，新运行不能继续使用。
- 用户在运行中失去权限：下一步和结果发送前重新校验，不能沿用初始授权。
- SSE 重复事件：客户端按 `event_id` 去重；服务端保证状态机单调或可解释回退。
- 浏览器重复提交：客户端幂等键与服务端运行创建约束防止重复执行。
- 连接器返回恶意或异常列名：白名单映射和转义；不得让列名进入前端代码。
- 模型返回超长计划或未知字段：Schema 拒绝，受预算约束重新规划或阻断。
- 记忆包含用户敏感信息：个人记忆与组织知识分区，默认最小保存和可删除审计。

## 9. 迁移、回滚与兼容边界

### 9.1 迁移顺序

1. 先建立 PostgreSQL migration 表和版本记录，不直接手工改生产表。
2. 先写入新的版本化对象（Binding、Context Pack、策略、计划 Schema），再
   切换读取指针；旧版本保持只读可回放。
3. 连接器或计划契约改变时，先支持双读/验证，再在明确门后切换写入。
4. 运行记录引用精确的策略、Context Pack、计划和来源版本，避免历史报告随
   当前资产漂移。

### 9.2 回滚边界

- 代码回滚：回到上一个已验收的 AlphaOx 版本；不回滚上游源码工作区外的
  用户数据。
- Schema 回滚：只允许已验证的逆迁移；不可逆数据删除必须另行批准。
- Context Pack 回滚：将发布指针切回上一版本，保留新版本和审计事件。
- 计划契约回滚：拒绝新版本计划并使用旧 Schema 重新规划；不能把未知字段
  静默降级成旧字段。
- Connector 回滚：禁用新连接器能力，保留 Snapshot 和失败 Trace；不得把
  未授权连接继续留在缓存。
- 前端回滚：结果块带 `payload_version`，旧前端遇到未知块应安全显示不可用，
  不能执行未知代码。

本路径不做数据删除、生产切换、真实企业连接或迁移执行，只冻结可回滚的
边界和顺序。

## 11. 可观测性、可访问性、清理与维护责任

### 11.1 可观测性

每个运行至少关联 `run_id`、`trace_id`、`user_id` 的脱敏标识、`org_id`、
策略版本、Context Pack 版本、模型提供商/模型标识、步骤状态、耗时、重试
次数、来源版本、`as_of`、错误类别和预算消耗。日志不得写入凭据、原始企业
行、完整提示词或未裁剪的文档内容。

指标首版只要求能回答：运行是否成功、在哪个步骤失败、来源是否过期、权限
拒绝多少、澄清多少、查询耗时和报告保存是否成功。健康检查区分进程健康、
控制面健康和可选数据源健康，不把外部来源失败伪装为服务健康。

### 11.2 可访问性

Web 工作台必须支持键盘完成提问、取消、重新连接、展开来源和阅读报告；
焦点顺序、可见焦点、语义标题、表格表头、图表替代表述、状态 live region、
错误文字和颜色对比必须可检查。颜色不是状态的唯一表达；`blocked`、`partial`
和 `stale` 必须有文字和图标/标记。动画默认尊重 reduced-motion，HTML 图形
提供静态阅读路径。

### 11.3 清理与数据生命周期

本路径只定义责任，不执行物理清理。未来实现必须分别处理临时查询结果、SSE
事件、Trace、个人记忆、组织知识、报告附件、连接器缓存和测试数据；每类
数据需要 owner、保留期、删除/撤销事件和恢复边界。任何清理脚本必须使用
明确范围和 dry-run，不能对 workspace 或整库递归删除。

### 11.4 维护责任

- AlphaOx maintainer：维护产品边界、计划/证据契约和上游同步记录。
- Connector owner：维护连接测试、能力声明、只读保证、Schema 漂移和新鲜度。
- Policy owner：维护身份、权限、脱敏、预算和审计规则。
- Web owner：维护结果块可访问性、响应式布局和 Browser 清单。
- Data steward：审核 Binding、业务术语、指标口径、版本和生效期。
- Release owner：维护依赖、镜像、迁移、回滚和发布前对抗审查。

任何 owner 变更都要更新审计和维护文档；不能由 Agent 根据最近提交者推断责任。
