# ContextOx 最小产品闭环 v0.1

> 状态：`APPROVED FOR MVP IMPLEMENTATION`
> 决策日：2026-09-01
> 适用范围：本地、单机、单发起人、单个明确批准者、自有 fixture

## 1. 产品决定

ContextOx 是业务定义形成与变更的执行 Agent，不是通用 ChatBI、自然语言 SQL 或自动替人决定业务规则的工具。

首个产品闭环沿用当前 Pi Coding Agent TUI 作为临时交互壳。Pi 继续展示对话、Agent 过程和工具调用；ContextOx 只补上产品不可缺少的领域状态与人工审批。

英文产品与未来仓库身份使用 **ContextOx**。**AlphaOx** 退为历史工程名称；当前本地目录、包名、Git remote、GitHub 仓库、域名和历史暂不改。中文 **数契** 继续作为工作品牌，尚未完成品牌确认。

## 2. 首个用户与任务

- 发起人：一个熟悉业务目标的专业用户。
- 批准者：一个在当前模拟范围内被明确配置为有权批准的人；这只是本地演示授权，不等于生产身份认证。
- 任务：基于自有确定性电商 fixture，从零建立“已有购买记录客户的高潜识别与运营优先级规范”。
- 起点：发起人给出模糊目标、范围和约束，没有现成适用 Contract。
- 终点：系统持久化一份经有效人工批准、可追溯且不可原地覆写的 `Contract v1`，或保留明确的拒绝、要求修改、阻塞或取消结果。

## 3. 最小闭环

```text
用户给出目标
  → Pi Agent 在授权工具内读取 fixture、形成候选规范与证据
  → Agent 调用 request_human_approval
  → ContextOx 冻结提案并持久化，Mission 进入 waiting_for_human
  → 人在 Pi TUI 中运行 /contextox-review 查看同一版本
  → approve / reject / request_changes
  → ContextOx 先持久化决定，再恢复 Agent
  → approve：事务性创建 Contract v1，Mission 完成
  → request_changes：生成新提案版本并重新审批
  → reject：保留明确终态或阻塞原因，不生成 Contract
```

人工等待可以跨 Pi 进程重启。关闭、分支、压缩或删除 Pi Session 不得修改 ContextOx 中已经持久化的审批和 Contract 事实。

## 4. 最小领域对象

首版只保留四个对象；一个 Mission 暂时对应一个 Definition Change Case，不建立通用工作流框架。

### Mission

保存目标、范围、约束、当前状态、当前提案版本和 Pi Session 引用。状态最少包括：

- `active`
- `waiting_for_human`
- `completed`
- `blocked`
- `cancelled`

### ApprovalRequest

保存冻结的提案版本、内容哈希、规范正文、证据引用、未知项、影响摘要、所需批准者、创建时间和状态。状态最少包括：

- `pending`
- `approved`
- `rejected`
- `changes_requested`
- `invalidated`

关键内容变化后，旧请求必须变为 `invalidated`，不得沿用旧批准。

### Decision

不可变地记录 `request_id`、预期提案版本与哈希、actor、`approve | reject | request_changes`、理由和决定时间。

相同决定的重复提交返回同一结果；不同结果的重复提交、错误 actor、过期版本或哈希不符必须 fail closed。

### ContractVersion

只有有效 `approve` 才能与 Decision 在同一事务中创建 `Contract v1`。它至少包含规范范围、规则、证据引用、未知与例外、样例/反例、批准者、批准时间和来源 ApprovalRequest。

Contract 创建后不可原地覆写。首版不实现既有 Contract 修订；后续修改必须创建新版本。

## 5. Pi TUI 复用边界

直接复用：

- Pi 的对话、流式输出、思考过程和工具调用展示；
- 项目级 extension 加载；
- 自定义 tool、command、entry renderer 和 TUI custom UI；
- `terminate: true` 停止审批后的自动续跑；
- `sendUserMessage` 在决定持久化后恢复 Agent；
- `session_start` 只用于恢复待审入口和展示。

ContextOx 新增：

- `request_human_approval` 工具；
- `/contextox-review` 命令和审批卡片；
- ContextOx 自有持久化与状态校验；
- Decision 与 Contract v1 的事务性创建；
- 失败、重复、过期和恢复测试。

首版不修改 `packages/agent`、`packages/tui` 或 `packages/coding-agent` 内核。只有公开 extension API 经实现证明不足时，才另行提出最小内核改动。

## 6. 持久化决定

首版使用 Node 内置 SQLite 能力和一个 ContextOx 自有本地数据库，不新增依赖，不复用 Pi Session 数据库作为领域真相。

运行数据库属于本地状态，不提交 Git。数据库初始化、版本和失败信息必须可检查；写入失败时保持原始错误，Mission 不得报告已等待、已批准或已完成。

PostgreSQL、事务 outbox、DBOS、Temporal 和多 Worker 并发均后置。只有单机闭环无法满足已经观察到的恢复、并发或运维要求时，才重新评估。

## 7. 必须成立的失败语义

- ApprovalRequest 未成功持久化：工具失败，Agent 不进入等待成功态。
- 没有有效批准：不得创建 Contract。
- 提案版本或哈希变化：旧请求失效，必须重新审批。
- 决定已持久化但 Agent 恢复失败：决定和 Contract 保留；下次启动可继续恢复，不重复决定。
- Pi Session 不可用：领域状态仍可读取，不把 Session 缺失解释为审批不存在。
- 模型、工具或解析失败：保留 `blocked`、`partial` 或原始错误，不包装成完成。
- TUI 展示失败：不改变业务状态；人可再次运行复核命令。
- 本地演示批准者不等于生产授权；进入真实试点前必须重新设计身份与权限。

## 8. MVP 验收

自动检查至少证明：

1. 提案先持久化，Agent 后停止；
2. 进程重启后仍能列出同一待审请求；
3. 正确 actor 对正确版本批准后只创建一个 Contract v1；
4. 无批准、错误 actor、过期版本、哈希不符和冲突重复决定均不创建 Contract；
5. `request_changes` 能产生新版本并使旧请求不可再批准；
6. 决定已落库但恢复消息失败时，可在下次启动继续；
7. Pi 原有过程与工具调用展示仍可用；
8. 测试使用 fake provider 或确定性工具，不把测试通过描述为真实模型能力。

人工验收至少证明：

1. 发起人能在 Pi TUI 输入目标并看到真实 Agent/工具过程；
2. 审批卡片能清楚显示冻结版本、范围、证据、未知和影响；
3. 批准、拒绝和要求修改三条路径的结果可理解、可恢复；
4. 重启后无需重做已完成决定；
5. 只有批准路径出现 Contract v1，且 Contract 能追溯到唯一 Decision。

自动检查与人工验收分别记录；人工未明确记录 `PASS` 前保持 `PENDING`。

## 9. 明确非目标

- Web、API、Worker、React Flow 或移动端；
- 多用户、SSO、组织级 RBAC、委托、通知与升级；
- PostgreSQL、DBOS、Temporal、消息队列或新依赖；
- 外部数据连接器、真实客户数据和付费模型能力评估；
- 下游发布、readback、回滚与效果观察；
- 既有 Contract 修订、通用流程平台、多 Agent；
- 当前本地目录、包名、远端仓库或 Git 历史重命名。

## 10. 下一决策门

本文件批准后，下一步只实施 Pi TUI 最小闭环。实现完成并通过自动检查后，由人执行 TUI 验收。

只有 TUI 闭环暴露出明确不足，才决定是否进入 Web、多用户、跨日分布式执行或外部发布。仓库整体迁移到 ContextOx、Pi fork 分离和远端重命名继续保持独立批准。
