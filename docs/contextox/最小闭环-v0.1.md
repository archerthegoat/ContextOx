# ContextOx 最小产品闭环 v0.1

> 状态：`APPROVED FOR MVP IMPLEMENTATION`
> 决策日：2026-09-01
> 适用范围：本地、单机、单发起人、单个明确批准者、自有 fixture

## 1. 产品决定

ContextOx 是业务定义形成与变更的执行 Agent，不是通用 ChatBI、自然语言 SQL 或自动替人决定业务规则的工具。

首个产品闭环由 ContextOx 应用作为唯一用户入口。用户运行 `./contextox-test.sh`（后续发布命令为 `contextox`）进入 ContextOx；ContextOx 拥有产品身份、配置入口、Session 创建策略、领域状态与人工审批，并在应用内部复用 Pi Coding Agent 的运行时、TUI 和 Pi Agent Core。Pi 是被嵌入的产品内核，不是外层产品；不得再通过运行 `./pi-test.sh`、创建一个名为 ContextOx 的 Pi role，或依赖项目级 `.pi` extension 来启动产品。

英文产品与仓库身份使用 **ContextOx**。GitHub 仓库已于 2026-09-01 从 `archerthegoat/alphaox` 重命名为 `archerthegoat/ContextOx`，本地 `origin` 已同步更新。**AlphaOx** 退为历史工程名称；当前本地目录、包名、域名和 Git 历史暂不改。中文 **数契** 继续作为工作品牌，尚未完成品牌确认。

## 2. 首个用户与任务

- 发起人：一个熟悉业务目标的专业用户。
- 批准者：一个在当前模拟范围内被明确配置为有权批准的人；这只是本地演示授权，不等于生产身份认证。
- 任务：基于自有确定性电商 fixture，从零建立“已有购买记录客户的高潜识别与运营优先级规范”。
- 起点：发起人给出模糊目标、范围和约束，没有现成适用 Contract。
- 终点：系统持久化一份经有效人工批准、可追溯且不可原地覆写的 `Contract v1`，或保留明确的拒绝、要求修改、阻塞或取消结果。

## 3. 最小闭环

```text
用户运行 ./contextox-test.sh 并给出目标
  → ContextOx 创建 Mission 与内部 Pi Session
  → 嵌入的 Pi Agent 在 ContextOx 授权工具内读取 fixture、形成候选规范与证据
  → Agent 调用 request_human_approval
  → ContextOx 冻结提案并持久化，Mission 进入 waiting_for_human
  → 人在 ContextOx TUI 中运行 /contextox-review 查看同一版本
  → approve / reject / request_changes
  → ContextOx 在同一事务中持久化决定与业务结果
      approve：创建 Contract v1，Mission 完成，resume_delivery=pending
      request_changes：Mission 恢复 active，resume_delivery=pending
      reject：Mission 保留 blocked 终态，不生成 Contract，resume_delivery=none
  → 仅 approve / request_changes 由 ContextOx adapter 恢复 Agent；成功标记 dispatched，失败保留 pending 与原始错误
```

人工等待可以跨 ContextOx 进程重启。内部 Pi Session 的关闭、分支、压缩或删除不得修改 ContextOx 中已经持久化的审批和 Contract 事实。

## 4. 最小领域对象

首版只保留四个对象；一个 Mission 暂时对应一个 Definition Change Case，不建立通用工作流框架。

### Mission

保存目标、范围、约束、当前状态、当前提案版本和 Pi Session 引用。它还保存独立的恢复投递状态 `none | pending | dispatched`、对应 request ID、最近投递错误与时间；这不是第五个领域对象。Mission 状态最少包括：

- `active`
- `waiting_for_human`
- `completed`
- `blocked`
- `cancelled`

### ApprovalRequest

保存冻结的提案版本、内容哈希、规范正文、证据引用、未知项、影响摘要、所需批准者、创建时间和状态。状态最少包括：

- `pending`
- `approved`
- `rejected`
- `changes_requested`
- `invalidated`

关键内容变化后，旧请求必须变为 `invalidated`，不得沿用旧批准。

### Decision

不可变地记录 `request_id`、预期提案版本与哈希、actor、`approve | reject | request_changes`、理由和决定时间。

相同决定的重复提交返回同一结果；不同结果的重复提交、错误 actor、过期版本或哈希不符必须 fail closed。

### ContractVersion

只有有效 `approve` 才能与 Decision 在同一事务中创建 `Contract v1`。它至少包含规范范围、规则、证据引用、未知与例外、样例/反例、批准者、批准时间和来源 ApprovalRequest。

Contract 创建后不可原地覆写。首版不实现既有 Contract 修订；后续修改必须创建新版本。

## 5. ContextOx 外壳与 Pi 内核复用边界

### 5.1 依赖方向与职责

```text
ContextOx CLI / product identity
  → ContextOx bootstrap、领域状态、审批与内部 Pi adapter
    → Pi Coding Agent SDK + InteractiveMode
      → Pi Agent Core
```

依赖只能向内指向 Pi；Pi 包不得依赖 ContextOx 领域代码。具体职责为：

| 边界 | 首版职责 | 不拥有 |
|---|---|---|
| `packages/contextox` | `contextox` CLI、产品身份、配置与状态路径、Session 创建策略、审批 UI 注册、启动/恢复 | 通用模型循环和通用 TUI |
| ContextOx 领域层 | Mission、ApprovalRequest、Decision、ContractVersion、SQLite 事务与 fail-closed 规则 | Pi Session 生命周期与终端渲染 |
| 现有 `semantic-agent` 复用面 | RuntimeHost、受控工具、证据/preflight 与 Pi adapter 的已验证部分；按需直接复用，不新建通用框架 | 产品入口和业务批准权 |
| Pi Coding Agent SDK / TUI | Session runtime、对话、流式输出、思考与工具调用展示、command/tool/renderer 扩展点 | ContextOx 领域真相和产品品牌 |
| Pi Agent Core | 模型调用、工具循环、事件、取消和停止条件 | Mission、审批、Contract 和产品配置 |

ContextOx 优先直接使用公开的 `createAgentSessionRuntime`、`InteractiveMode` 和 inline extension 接缝，在应用 bootstrap 中注册 `request_human_approval`、`/contextox-review`、`/contextox-resume` 与 renderer。bootstrap 必须构造隔离的 `DefaultResourceLoader`：`noExtensions`、`noSkills`、`noPromptTemplates`、`noContextFiles` 均开启，只注入 ContextOx inline factory；不得发现项目或全局 extension、skill、prompt template 和 context file。Agent tools 使用显式 allowlist，首版只启用 `read_contextox_fixture` 与 `request_human_approval`，不得继承默认 `read`、`bash`、`edit`、`write`。

ContextOx CLI 在创建 Pi runtime 前解析产品自己的 `--actor <actor-id>` 与 `--approver <approver-id>`，生成不可变的本地 ActorContext 和 ApprovalPolicy。两项缺失都 fail closed；ApprovalRequest 的 required approver 由 ApprovalPolicy 注入，不接受模型工具参数覆盖。Decision actor 只来自 ActorContext，Pi flag、Pi Session metadata、聊天文本和模型输出都不是授权来源。这个本地显式配置只用于 MVP 演示，不构成生产认证。

`terminate: true` 只停止本次 Agent 续跑。`approve` 与 `request_changes` 的 Decision 事务把 Mission 的恢复投递标记为 `pending`；审批结果 `reject` 保持 `none`，不得再触发 Agent turn。恢复必须由 ContextOx adapter 调用并等待 `runtime.session.sendUserMessage()`；不得用返回 `void` 的 `ExtensionAPI.sendUserMessage` 作为成功凭证。awaitable 调用成功 resolve 后才标为 `dispatched`，调用抛错或 Promise reject 时保留 `pending` 和原始错误。启动时列出 pending 恢复项，`/contextox-resume <request-id>` 通过同一 adapter 以当前内部 Session 重试；已 dispatched 的 request 不重复发送。Pi 运行接缝不成为领域状态源。

Pi Coding Agent 当前公开 SDK 已支持嵌入其他应用，但标题、页眉和部分配置仍读取静态 Pi identity。若实现证明无法通过现有公开参数显示完整 ContextOx 身份，允许在 `packages/coding-agent` 增加一个最小、通用、可选的 app-identity 注入接缝；默认行为必须保持 Pi 不变。不得把 ContextOx 领域规则写入 `packages/coding-agent`，也不得修改 `packages/agent` 或 `packages/tui`，除非另有证据和批准。

现场依据：[`packages/coding-agent/docs/sdk.md`](../../packages/coding-agent/docs/sdk.md) 明确支持嵌入式使用；[`packages/coding-agent/src/index.ts`](../../packages/coding-agent/src/index.ts) 导出 runtime 与 `InteractiveMode`；[`packages/coding-agent/src/config.ts`](../../packages/coding-agent/src/config.ts) 和 [`interactive-mode.ts`](../../packages/coding-agent/src/modes/interactive/interactive-mode.ts) 显示当前产品 identity 为静态 Pi 常量；[`extensions/types.ts`](../../packages/coding-agent/src/core/extensions/types.ts) 与 [`agent-session.ts`](../../packages/coding-agent/src/core/agent-session.ts) 分别证明 extension API 的发送返回 `void`、runtime session 的发送可等待；[`packages/semantic-agent`](../../packages/semantic-agent) 已有 ContextOx 可复用的确定性运行边界。以上是当前仓库事实，不是运行验收。

### 5.2 选择与取舍

| 方案 | 结论 | 取舍 |
|---|---|---|
| Pi CLI + ContextOx role / 项目级 extension | 拒绝 | 启动、身份和能力发现仍属于 Pi，ContextOx 只是一个项目角色，不是产品 |
| ContextOx 外壳嵌入 Pi runtime/TUI/core | 采用 | 最小复用现有内核和 UI；需要维护一个薄 adapter，并可能补一个通用 identity 接缝 |
| 自写 ContextOx TUI 或 Agent 内核 | 拒绝 | 重复已经可用的 Pi 能力，扩大首个闭环 |
| 立即拆成 ContextOx app repo + 独立 Pi fork | 后置 | 是路径七的目标候选，但当前会把产品闭环与历史、供应链和远端迁移绑在一起 |

### 5.3 实现迁移与回滚

1. 新增 `packages/contextox` 和根入口 `contextox-test.sh`，先建立 ContextOx 自有 bootstrap 与产品 identity。
2. 将当前 `.pi/contextox/*` 原型中可用的领域存储与测试迁入 ContextOx 包；审批 tool/command/renderer 由应用内部注册。
3. 只有静态 Pi identity 被实测证明为阻塞时，才增加通用 identity 接缝并用 Pi 默认行为回归测试保护。
4. 新入口实现与验收期间保留 `.pi/extensions/contextox.ts` 和 `.pi/contextox/*` 作为只读诊断原型，但 ContextOx resource loader 必须证明它们未被加载。新入口通过后，再向人展示这些旧原型的精确删除 diff 并单独批准。

回滚只撤销新 ContextOx 包、根入口和可选 identity 接缝，不迁移或删除已有业务数据库。回滚后产品状态为 `BLOCKED`，不得重新把 Pi CLI 原型宣称为 ContextOx 产品；保留的旧原型只用于比较和诊断。首版 SQLite schema 与领域规则保持兼容；若迁移前后状态读回不一致，则停止切换，不宣称闭环完成。

## 6. 持久化决定

首版使用 Node 内置 SQLite 能力和一个 ContextOx 自有本地数据库，不新增依赖，不复用 Pi Session 数据库作为领域真相。

运行数据库属于本地状态，不提交 Git。数据库初始化、版本和失败信息必须可检查；写入失败时保持原始错误，Mission 不得报告已等待、已批准或已完成。

PostgreSQL、事务 outbox、DBOS、Temporal 和多 Worker 并发均后置。只有单机闭环无法满足已经观察到的恢复、并发或运维要求时，才重新评估。

首版运维边界：

- 权限：隔离 ResourceLoader 只加载 ContextOx inline factory；显式工具 allowlist 只允许 fixture reader 与 approval tool。当前 actor 和 required approver 由 ContextOx CLI/config 绑定，产品 bootstrap 不继承 Pi flag、Session、项目/全局资源或默认工具权限。
- 新鲜度：证据保留来源、记录时间和业务时间；fixture 之外没有当前数据时保持 `UNKNOWN`，不伪造实时性。
- 可观测性：终端和测试记录 Mission/request/decision/contract 标识、状态转换与原始错误；默认不记录 secret 或原始敏感数据。
- 可访问性：审批与状态必须有完整纯文本、键盘可达表达，不依赖颜色或鼠标；窄终端不得隐藏决定所需字段。
- 清理：自动验收只使用独立临时状态目录；只删除该次测试创建的目录，不清理用户数据库、Pi Session 或其他工作树文件。
- 所有权：ContextOx 维护产品入口、领域状态、审批与 adapter；Pi 上游维护通用 runtime/TUI/core。升级和仓库分离继续按路径七单独审议。

## 7. 必须成立的失败语义

- ApprovalRequest 未成功持久化：工具失败，Agent 不进入等待成功态。
- ContextOx bootstrap、内部 adapter 或产品 identity 初始化失败：不得退回 Pi CLI 冒充成功启动，也不得创建 Mission。
- 没有有效批准：不得创建 Contract。
- 提案版本或哈希变化：旧请求失效，必须重新审批。
- approve 或 request_changes 已持久化但 Agent 恢复失败：决定和 Contract 保留，Mission.resume_delivery 保持 `pending` 并保存原始错误；下次启动列出该 request，由 `/contextox-resume <request-id>` 通过 awaitable adapter 重试，成功后标记 `dispatched`，不得重复决定或重复投递已 dispatched 项。reject 保持 `none`，不得启动新 Agent turn。
- Pi Session 不可用：领域状态仍可读取，不把 Session 缺失解释为审批不存在。
- 模型、工具或解析失败：保留 `blocked`、`partial` 或原始错误，不包装成完成。
- TUI 展示失败：不改变业务状态；人可再次运行复核命令。
- 本地演示批准者不等于生产授权；进入真实试点前必须重新设计身份与权限。

## 8. MVP 验收

自动检查至少证明：

1. `./contextox-test.sh --help` 和交互启动都显示 ContextOx identity，且不是调用 `./pi-test.sh` 的别名；
2. 当前 `.pi/extensions/contextox.ts` 保持原位时，ContextOx 已加载资源来源中只有显式 inline factory；项目/全局 extension、skill、prompt template、context file 均未加载；
3. 提案先持久化，Agent 后停止；
4. 进程重启后仍能列出同一待审请求；
5. `--actor` 与 `--approver` 由 ContextOx 解析并绑定；缺失配置、错误 actor、Pi flag/Session/模型伪造 actor 均 fail closed；
6. 正确 actor 对正确版本批准后只创建一个 Contract v1；
7. 无批准、错误 actor、过期版本、哈希不符和冲突重复决定均不创建 Contract；
8. `request_changes` 能产生新版本并使旧请求不可再批准；
9. 强制 ContextOx adapter 的 `runtime.session.sendUserMessage()` reject 后，重启能列出同一 pending 恢复项；`/contextox-resume <request-id>` 成功后标记 dispatched，第二次调用不重复投递；reject 路径不调用该 adapter；
10. active tools 精确等于两个 ContextOx tools，默认 `read`、`bash`、`edit`、`write` 不可用；
11. Pi 原有对话、流式输出和已获准工具调用展示在 ContextOx TUI 内仍可用；
12. Pi 默认入口的 identity 与行为回归不受可选注入接缝影响；
13. 测试使用 fake provider 或确定性工具，不把测试通过描述为真实模型能力。

Agent 代行 TUI 验收使用旁路终端，且不得写成人类验收：

1. 记录精确 branch、HEAD、工作树差异和启动命令；使用一个 `contextox-mvp` tmux session，先以 80×24、再以 120×36 检查，终端缩放保持默认；Browser/URL 不适用。
2. 从独立临时状态目录以 ContextOx `--actor` / `--approver` 启动 `./contextox-test.sh`，确认页眉、terminal title、帮助和主命令均为 ContextOx；不出现“ContextOx 只是 Pi role”的启动路径。
3. 检查加载来源只含 ContextOx inline factory，active tools 只含两个 ContextOx tools；仓库现有 `.pi` extension 和任意全局资源均未加载，默认文件/shell/写入工具不可调用。
4. 使用 fake provider 与自有 fixture 依次走创建 Mission、展示真实工具过程、冻结审批、退出、重启、`/contextox-review`、approve；另用隔离状态分别检查 reject、request_changes、错误 actor 与缺失 actor/approver。
5. 在 approve/request_changes 事务成功后强制 awaitable adapter 恢复失败，退出并重启；确认 pending 恢复项可见，运行 `/contextox-resume <request-id>` 后变为 dispatched，重复命令不再次投递；reject 后确认没有 Agent turn 和待恢复项。
6. 检查键盘输入、焦点返回、长审批卡片滚动、窄/宽终端可读性；核心字段不得只靠颜色表达，鼠标不是完成审批的必要条件。
7. 检查 loading、empty、partial、error、stale/invalidated 和恢复失败；每种状态显示下一步且不改变既有业务事实。
8. 检查 stderr/诊断输出和意外网络请求；fake 验收不得调用真实模型、付费 API 或外部写入。
9. 读回 SQLite，确认只有批准路径存在唯一 Contract v1，并能追溯唯一 Decision；保存 terminal transcript、加载来源、active tools、命令退出状态和数据库读回摘要。
10. 结束 tmux，只清理本次独立临时目录；记录每项 `PASS | FAIL | BLOCKED`、证据路径和限制。任何 FAIL/BLOCKED 都不得汇总成通过。

人工产品验收默认仍为 `PENDING`。用户已授权 Agent 运行上述 TUI 验收，因此可以单独记录 `AGENT TUI ACCEPTANCE: PASS | PARTIAL | BLOCKED`，但不能替代或暗示人类 `PASS`。

## 9. 明确非目标

- Web、API、Worker、React Flow 或移动端；
- 自写 ContextOx TUI、重写 Pi Agent Core，或把首个闭环拆成多个服务；
- 多用户、SSO、组织级 RBAC、委托、通知与升级；
- PostgreSQL、DBOS、Temporal、消息队列或新依赖；
- 外部数据连接器、真实客户数据和付费模型能力评估；
- 下游发布、readback、回滚与效果观察；
- 既有 Contract 修订、通用流程平台、多 Agent；
- 当前本地目录、既有包名、域名、Git 历史重写或仓库拆分；GitHub 仓库重命名已经单独批准并完成。

## 10. 下一决策门

本文件精确修订获批后，下一步只实施 ContextOx 外壳包裹 Pi runtime/TUI/core 的最小闭环：新增 ContextOx 包与命令、迁移当前项目 extension 原型中的逻辑但保留原型文件用于诊断、在必要时增加通用 identity 接缝，并运行自动检查与 Agent 代行 TUI 验收。旧原型删除另行展示精确 diff。该批准不包含 commit、push、真实模型/数据、外部写入、仓库拆分或发布。

只有 ContextOx TUI 闭环暴露出明确不足，才决定是否进入 Web、多用户、跨日分布式执行或外部发布。本地目录与既有包名迁移、ContextOx app 与 Pi fork 分离、域名及历史处理继续保持独立批准。
