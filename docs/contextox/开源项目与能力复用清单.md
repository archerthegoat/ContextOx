# ContextOx 开源项目与能力复用清单

> 状态：`RESEARCH INPUT / NO DEPENDENCY APPROVED`
> 研究基准日：2026-08-30
> 目的：识别可复用能力、边界和许可证风险；本清单不授权安装、升级、复制代码、改变架构或选定供应商。

关联文档：[产品方向与同类产品](./产品方向与同类产品.md) · [PRD v0.1](./PRD-v0.1.md) · [Pi 内核与上游同步策略](./Pi内核与上游同步策略.md)

## 1. 结论先行

ContextOx 不应从零重建 Agent runtime、持久工作流、数据目录、指标引擎、策略系统、身份系统、通知平台或可观测平台；也不应因为项目活跃或流行就立即把它们引入运行时。

当前最小结论是：

1. **保留现有 Pi Agent Core 薄适配边界**，不同时引入第二套 Agent runtime；当前仓库中的直接 Pi 绑定只是内部类型适配和开发依赖，不代表生产运行已完成。
2. **目录、血缘、指标、策略、身份、通知和观测优先采用适配器边界**，把成熟项目视为集成目标或设计参照，而不是复制到 ContextOx 内核。
3. **持久长流程是必须解决的问题，但不是必须立即引入 Temporal/Trigger.dev 的结论。** 先用真实试点确认暂停、重试、超时、补偿和多日人工任务的复杂度，再走架构决策门。
4. **强 copyleft、source-available 和 open-core 项目必须逐文件/逐功能审查。** “GitHub 可见”不等于可自由嵌入或提供托管服务。
5. **活跃度只是维护风险信号，不是安全、质量、合规或适配性的证明。** 星标和最近提交均为基准日快照。

## 2. 复用方式定义

| 方式 | 含义 | 当前授权状态 |
|---|---|---|
| `DIRECT DEPENDENCY` | 作为运行时或开发依赖直接安装和调用 | 只有仓库既有依赖；新增均未批准 |
| `ADAPTER TARGET` | ContextOx 通过稳定接口连接客户已部署的系统 | 候选方向，具体协议和首批目标未批准 |
| `REFERENCE` | 学习领域模型、失败语义、测试或运维方式，不复制受限代码 | 允许研究；实施需单独评审 |
| `ADAPT SMALL PART` | 在许可证允许且价值明确时复用小型库或格式 | 必须做代码、许可证和供应链审查 |
| `NOT RECOMMENDED NOW` | 当前重叠、风险或运维成本高于已证实价值 | 不是永久否决，可由新证据重开 |

## 3. 评估标准

每个候选至少回答：

- 它解决哪个明确问题，哪些问题不解决；
- 当前维护活动和成熟度有什么公开证据；
- 根许可证、子目录、企业功能和托管限制分别是什么；
- 与现有 `semantic-agent`、Pi 或未来 ContextOx 领域核心重叠多少；
- 最小集成接缝是什么；
- 失败、升级、数据迁移和退出时如何解耦；
- 引入后谁负责运行、补丁、告警、备份和安全响应。

## 4. Agent runtime 与多 Agent

| 项目 | 能力与边界 | 活跃度/成熟度信号 | 许可证与商业风险 | 复用判断 | 重叠与最小接缝 |
|---|---|---|---|---|---|
| [earendil-works/pi](https://github.com/earendil-works/pi) | TypeScript Agent Core、模型与工具循环、事件流；不提供 ContextOx 的业务定义领域、持久协作或企业控制面 | 基准日约 9.9 万 stars，2026-08-29 仍有提交；当前上游版本 0.84.4 | MIT；仍需锁定版本、审查依赖和上游变更 | `DIRECT DEPENDENCY` 候选仅限 Pi Agent Core；**保持当前薄适配，不引入上游整仓作为产品内核** | 与 `RuntimeHost`/loop 有边界相邻；最小接缝是 AlphaOx-owned event adapter + fake stream contract tests |
| [LangGraph.js](https://github.com/langchain-ai/langgraphjs) | 图式、状态化 Agent 编排和持久执行抽象；不提供业务治理领域模型 | 基准日约 3.2k stars，2026-08-26 仍有提交 | MIT；与 LangChain 生态耦合和版本面需评估 | `REFERENCE / NOT RECOMMENDED NOW` | 与现有 Pi loop 和未来持久工作流重叠；只研究 checkpoint、interrupt、resume 语义，不同时运行两套 Agent runtime |
| [Mastra](https://github.com/mastra-ai/mastra) | TypeScript Agent、workflow、memory、evals 等一体框架 | 基准日约 2.8 万 stars、持续更新 | 核心 Apache-2.0；`ee/` 等企业部分另有许可，需逐路径确认 | `REFERENCE / NOT RECOMMENDED NOW` | 与 Pi、观测和工作流多处重叠；最小接缝仅为模式比较，不直接依赖 |

### 当前决策边界

- 现阶段没有证据支持“多 runtime 并存”。
- “多 Agent”不是产品目标本身。只有当一个 Definition Change Case 的职责、权限和失败隔离需要多个受控执行体时，才定义角色化 Agent；不得用多个 Agent 模拟未建模的领域状态机。
- ContextOx 的领域事件、权限、证据和发布语义必须由自身契约掌握，不能依赖某个 Agent 框架的内部消息格式。

## 5. 人类任务、审批、提醒与长流程

| 项目 | 能力与边界 | 活跃度/成熟度信号 | 许可证与商业风险 | 复用判断 | 重叠与最小接缝 |
|---|---|---|---|---|---|
| [Temporal](https://github.com/temporalio/temporal) | Durable execution、重试、timer、signal、补偿和长时间 workflow；不替代业务状态机、权限或 UI | 基准日约 2.3 万 stars；多语言 SDK 与生产生态成熟 | Server MIT；托管服务和运维成本另计 | `REFERENCE / EVALUATE AFTER PILOT` | 可能承载 Case 执行但不拥有 Definition Contract；最小接缝是领域 command/event port，禁止把 Temporal history 当唯一业务审计 |
| [Trigger.dev](https://github.com/triggerdotdev/trigger.dev) | TypeScript 长任务、队列、调度、等待和开发者工作流 | 基准日约 1.6 万 stars、持续更新 | Apache-2.0；云服务、部署和版本兼容需另评估 | `REFERENCE / EVALUATE AFTER PILOT` | 与 Node/TS 栈贴近；最小接缝是 job adapter，不把产品状态只保存在 job metadata |

### 必须先从试点取证的问题

- 人类任务是否会跨天、跨周暂停；
- 是否需要可靠 reminder、升级、委托和组织变更处理；
- 同一个案例是否有并行任务、撤销、重开和人工补偿；
- 发布失败后需要技术重试还是业务回滚；
- 客户要求 SaaS、私有化、离线或信创部署中的哪一种；
- 谁承担工作流引擎的数据库、备份、升级和灾备。

在这些约束明确前，直接选择引擎会过早冻结运维架构。

## 6. Catalog、Glossary、Owner、Lineage 与 Impact

| 项目 | 能力与边界 | 活跃度/成熟度信号 | 许可证与商业风险 | 复用判断 | 重叠与最小接缝 |
|---|---|---|---|---|---|
| [DataHub](https://github.com/datahub-project/datahub) | 元数据图、目录、所有权、术语、血缘、事件/API；商业 Context Platform 另有产品能力 | 基准日约 1.3 万 stars、持续更新；大型生产社区 | Core Apache-2.0；商业云/企业能力条款另行确认 | `ADAPTER TARGET` | 不复制其目录；通过 metadata/event API 读取资产、Owner、血缘，写回只允许预览后授权 |
| [OpenMetadata](https://github.com/open-metadata/OpenMetadata) | 目录、连接器、术语、血缘、质量、治理和 API | 基准日约 1.5 万 stars、持续更新 | Apache-2.0；运行栈和连接器供应链较大 | `ADAPTER TARGET` | 与 L1 发现能力重叠；最小接缝是只读 inventory/lineage port，写入作为独立 capability |

### 边界

ContextOx 只需要：

- 统一的 `AssetRef`、`OwnerRef`、`LineageEdge`、`Freshness` 和来源证明；
- 可替换的 catalog connector；
- 影响候选与来源系统状态分离；
- 未连接、权限不足、部分返回和陈旧状态显式可见。

ContextOx 不应自己实现所有数据库扫描器、血缘解析器和全企业目录 UI。DataHub/OpenMetadata 也不应成为业务定义契约的唯一真相源，除非经过单独产品和架构决策。

## 7. Metrics、Semantic Layer、Business Rules 与 Data Contracts

| 项目 | 能力与边界 | 活跃度/成熟度信号 | 许可证与商业风险 | 复用判断 | 重叠与最小接缝 |
|---|---|---|---|---|---|
| [MetricFlow](https://github.com/dbt-labs/metricflow) | 指标语义模型、维度和查询规划；不处理跨角色定义形成 | 基准日约 1.8k stars、持续维护 | Apache-2.0；与 dbt 产品/语义层版本边界需确认 | `ADAPTER TARGET / REFERENCE` | Business Definition Contract 可编译出 metric proposal；最小接缝是版本化模型 diff + compile/validate result |
| [Cube](https://github.com/cube-js/cube) | 语义层、缓存、查询 API 和访问控制；不提供完整治理协作 | 基准日约 2.1 万 stars、持续更新 | 仓库声明按文件/包使用 Apache-2.0 或 MIT；必须逐文件核验，商业产品另计 | `ADAPTER TARGET / REFERENCE` | 最小接缝是 semantic model export/diff/test；不把 Cube schema 当跨系统唯一契约 |
| [Data Contract CLI](https://github.com/datacontract/datacontract-cli) | Data Contract 规范的 lint、test、export 与多格式工具；主要面向数据产品接口 | 基准日约 1k stars、持续维护 | MIT；格式和插件兼容需验证 | `ADAPT SMALL PART / REFERENCE` | 可作为下游数据契约验证器；Business Definition Contract 保持独立上层对象，通过明确映射生成其输入 |

### 边界

业务定义契约不应发明另一个通用 SQL/指标引擎。它需要定义可移植的上层语义和控制字段，再通过目标适配器生成：

- metric/semantic model 变更候选；
- data contract 或 schema policy；
- glossary/term 版本；
- Agent context 或检索过滤；
- 人类可读说明与测试样例。

编译必须可预览、可验证、目标级授权、可重试且可回滚；任何格式采纳都需独立兼容性决策。

## 8. Policy、Identity 与 Audit

| 项目 | 能力与边界 | 活跃度/成熟度信号 | 许可证与商业风险 | 复用判断 | 重叠与最小接缝 |
|---|---|---|---|---|---|
| [OpenFGA](https://github.com/openfga/openfga) | 关系型授权模型和检查 API；不负责认证和业务审批 | 基准日约 5.7k stars、持续维护 | Apache-2.0；模型迁移、缓存和一致性语义需评估 | `REFERENCE / ADAPTER CANDIDATE` | 最小接缝是 `AuthorizationDecision` port，领域事件仍记录主体、资源、动作、模型版本和结果 |
| [Open Policy Agent](https://github.com/open-policy-agent/opa) | 通用策略即代码与决策 API；不管理用户身份或业务任务 | 基准日约 1.2 万 stars、成熟生态 | Apache-2.0；Rego 学习和策略运营成本 | `REFERENCE / ADAPTER CANDIDATE` | 可承载发布/数据用途 guardrail；最小接缝是输入摘要、策略包版本、决策和理由 |
| [Keycloak](https://github.com/keycloak/keycloak) | 身份、SSO、OIDC/SAML、用户和组织能力；不替代细粒度领域授权模型 | 基准日约 3.6 万 stars、成熟部署 | Apache-2.0；Java 运行栈和自托管运维成本明显 | `ADAPTER TARGET` | ContextOx 使用标准 OIDC claims；不把 Keycloak 用户对象直接泄漏到领域模型 |

### 审计要求

无论采用哪个外部系统，ContextOx 必须保留自身领域审计：

- 谁在何时、基于哪个身份与授权模型发起动作；
- 输入证据、模型/工具版本和策略决策摘要；
- 哪个 Case、Contract、Task、Release 和目标受影响；
- 部分失败、重试、撤销、回滚和人工覆盖；
- 敏感原文不进入普通日志，审计事件可做保留策略和访问控制。

IAM 或 policy engine 的日志不能替代业务决定链。

## 9. Forms、Notifications 与 Collaboration

| 项目 | 能力与边界 | 活跃度/成熟度信号 | 许可证与商业风险 | 复用判断 | 重叠与最小接缝 |
|---|---|---|---|---|---|
| [Novu](https://github.com/novuhq/novu) | 多渠道通知、偏好和工作流；不拥有 Definition Case 任务状态 | 基准日持续更新、社区规模大 | Core MIT；enterprise/EE 目录与商业功能另有许可 | `ADAPTER CANDIDATE` | 最小接缝是幂等 `NotificationRequest` 与 delivery receipt；提醒失败不改变任务真相 |
| [Formbricks](https://github.com/formbricks/formbricks) | 表单、调查和反馈收集；不提供业务审批或动态案例编排 | 基准日持续更新 | 核心默认 AGPLv3，部分 SDK/API 为 MIT，EE 目录另行许可；托管/分发需要法律审查 | `REFERENCE / NOT RECOMMENDED TO EMBED NOW` | 研究 microtask 的低摩擦输入；优先自有最小表单或外部链接 adapter，避免无意引入 copyleft 边界 |

### 集成原则

- 飞书、钉钉、企业微信、邮件或工单是交付渠道，不是业务状态源；
- 所有 task completion 必须带幂等键、主体、版本和服务端校验；
- 链接过期、重复点击、转发、离职、委托、渠道失败和消息撤回都需有显式状态；
- 不在通知正文泄漏敏感证据；默认只给摘要和受控入口；
- 先从一个试点渠道取证，再决定是否引入通知平台。

## 10. Tracing、Evals 与 Observability

| 项目 | 能力与边界 | 活跃度/成熟度信号 | 许可证与商业风险 | 复用判断 | 重叠与最小接缝 |
|---|---|---|---|---|---|
| [OpenTelemetry JS](https://github.com/open-telemetry/opentelemetry-js) | 标准 trace、metric、log API/SDK 与导出；不提供 Agent 领域评估 | 基准日约 3.5k stars、CNCF 生态成熟 | Apache-2.0；collector/backend 另选 | `ADAPT SMALL PART / FIRST CANDIDATE` | 在现有 `TraceStore` 外定义 OTel adapter；领域 trace ID 稳定，敏感字段先最小化再导出 |
| [Langfuse](https://github.com/langfuse/langfuse) | LLM tracing、prompt、evaluation、dataset 等 | 基准日持续更新、生产用户生态 | core（`ee` 外）MIT；企业能力另有许可/密钥边界 | `ADAPTER CANDIDATE` | 可接收脱敏 Agent spans；不能成为审计或业务结果唯一存储 |
| [Arize Phoenix](https://github.com/Arize-ai/phoenix) | LLM/ML tracing、evals 和可视化 | 基准日持续更新；平台偏 Python，含 TS 客户端 | Elastic License 2.0，限制以托管/管理服务形式提供；与“无 Python runtime”方向冲突 | `REFERENCE / NOT RECOMMENDED AS CORE NOW` | 如使用仅经 OTel/OpenInference export adapter；先做法律和运行栈评审 |

### 观测分层

必须区分：

1. **业务审计**：谁决定了什么，属于 ContextOx 领域真相；
2. **Agent trace**：模型、工具、token、延迟、错误和步骤；
3. **产品指标**：案例周期、任务返工、发布与采用；
4. **业务结果信号**：例如高潜客户覆盖、转化或投诉，不能未经设计直接归因；
5. **基础设施遥测**：服务、队列、数据库和适配器健康。

外部观测平台可以承接 2 和 5 的部分能力，但不得吞并 1。

## 11. 当前能力与复用映射

| ContextOx 所需能力 | 当前 `semantic-agent` 基线 | 最小下一接缝 | 是否已批准实现 |
|---|---|---|---|
| Agent runtime | `RuntimeHost`、Pi adapter boundary、受控工具和 loop | 保持 AlphaOx-owned event schema；Pi fake stream contract test | 既有基线；生产集成未完成 |
| Source/catalog | SourceConnector、Snapshot、Binding、ContextPack | `CatalogConnector` 适配器族与来源/权限/部分状态 | 否 |
| 影响模拟 | AnalysisPlan、QueryPlan、preflight、fixture executor | 将查询/映射证据挂到 Definition Change Case，而非直接变成产品真相 | 否 |
| 证据/追踪 | EvidenceEnvelope、TraceStore（内存） | 持久领域审计 + OTel 脱敏导出 | 否 |
| 人类任务/审批 | 缺失 | Task/Decision command-event port；渠道 adapter | 否 |
| 持久长流程 | 缺失 | 可恢复 Case state machine；引擎可替换 | 否 |
| 身份/策略 | 只有受控工具边界，没有企业 IAM | OIDC identity + policy decision port | 否 |
| 通知/协作 | 缺失 | 幂等 notification/task link adapter | 否 |
| 契约发布 | Binding/ContextPack 有生命周期与回滚思路 | 多目标 compile/preview/authorize/publish/verify/rollback port | 否 |
| 结果反馈 | 缺失 | OutcomeSignal + measurement provenance | 否 |

## 12. 推荐的研究顺序，而非实施顺序

1. 用高潜客户试点画出真实 Case、角色、等待时间、失败和系统边界；
2. 只实现可证伪的一条端到端 seam，外部系统优先用 fixture 或只读 adapter；
3. 根据长任务证据决定是否评估 Temporal 或 Trigger.dev；
4. 根据客户现有栈选择一个 catalog/metric/collaboration 目标，不同时做通用连接器矩阵；
5. 在首次真实发布前完成身份、策略、审计和回滚架构决策；
6. 在遥测字段和数据出境边界明确后，再选择 Langfuse/Phoenix 等后端。

## 13. 采用前检查单

任何新增项目必须单独通过：

- [ ] 真实用户案例证明该能力不能由更小实现或现有客户系统满足；
- [ ] 读取目标版本 release notes、许可证和企业功能边界；
- [ ] 依赖树、安装脚本、已知漏洞和供应链来源审查；
- [ ] 数据路径、遥测、模型调用和跨境/私有化要求确认；
- [ ] 失败、重试、幂等、部分成功、迁移和回滚测试；
- [ ] 定义一个可替换的 ContextOx-owned port，而不是传播第三方类型；
- [ ] 明确部署、升级、备份、告警和安全响应 Owner；
- [ ] 精确版本锁定并建立上游同步节奏；
- [ ] 记录已批准的架构决策与人工验收；
- [ ] 未满足任一关键门时保持 `PENDING`，不以 demo 成功替代生产可用。
