# ContextOx（数契）产品定义与品牌核心

> 状态：`DRAFT / PENDING PRODUCT AND BRAND GATE`
> 基准日：2026-08-30
> 约束：本文件定义候选产品与品牌方向，不批准重命名、架构、商业模式或对外发布。

关联文档：[产品方向与同类产品](./产品方向与同类产品.md) · [PRD v0.1](./PRD-v0.1.md)

## 1. 一句话定义

**数契（ContextOx）是面向中大型组织的业务定义变更协作 Agent：它把一次模糊的业务口径变化转成有人负责、有证据、有争议记录、有生效时间、可发布、可回滚、可观察的业务定义契约。**

更短的内部表达：

> 让业务定义的形成、变化和落地成为一个可执行的过程。

该类别暂称 **Business Definition Operations（业务定义运营）** 或 **Business Definition Change Control（业务定义变更控制）**。类别名称仍需客户语言测试；在验证前不对外宣称已建立新品类。

## 2. 产品不是解决“问不到答案”，而是解决“答案凭什么成立”

### 问题

企业可以购买更强的模型、ChatBI、目录和指标平台，但当“高潜客户”“有效商机”“活跃用户”“合格供应商”发生变化时，系统仍需要人回答：

- 哪个口径对哪个范围有效；
- 谁有权作决定；
- 哪些证据支持或反对它；
- 它影响哪些数据、报表、模型、Agent 和流程；
- 何时生效，旧版本如何追溯或回滚；
- 发布后是否真的改善结果。

### 产品解法

数契以 Definition Change Case 组织整个过程。Agent 负责发现证据与缺口、拆分微任务、匹配责任人、追踪超时、汇总争议、模拟影响、生成候选契约和监督发布条件；人类保留业务真相、授权和高风险动作的最终决定权。

### 必要性

如果没有这一层，Agent 只能把组织内未解决的定义冲突更快地传播到查询、报表和自动化中。数契的价值不是再生成一份描述，而是把“形成有效定义”变成可审计的组织能力。

## 3. 核心客户假设

以下均为 `PRODUCT HYPOTHESIS`，需要以真实访谈、采购路径和付费试点验证。

### 3.1 初始 ICP

优先候选：

- 已有数据仓库/湖仓、指标平台、数据目录或治理团队；
- 至少三个业务或职能团队共享同一关键定义；
- 口径变化会影响报表、模型、Agent、营销/销售动作或合规判断；
- 当前主要依赖会议、群聊、工单和人工 SQL 对齐；
- 能指定业务 Owner、数据 Owner、安全/合规和发布责任人；
- 愿意以一个真实案例提供基线、最小系统接入和结果反馈。

中国市场的优先组织类型：

- 数据成熟度较高的中大型互联网与科技企业；
- 金融、制造、能源、零售等多业务线或受监管企业；
- 有数据要素、标准或内部数据库改革项目的国企和政府单位；
- 能通过咨询、FDE 或行业伙伴进入的复杂组织。

### 3.2 暂不优先

- 个人用户与消费者；
- 尚无稳定数据 Owner、系统边界或共同业务对象的早期团队；
- 只需要一次性报表或自然语言 SQL 的客户；
- 没有授权提供证据、人员协作或任何下游验证的“纯展示”项目；
- 把“Agent 自动替人决定业务规则”作为硬需求的客户。

不优先不等于永不服务；它表示当前产品价值与实施成本尚不匹配。

## 4. 购买与使用角色

| 角色 | 典型目标 | 主要阻力 | 数契提供的候选价值 |
|---|---|---|---|
| 经济购买者：CDO/CIO、数字化负责人、数据治理负责人 | 降低跨部门治理和错误口径成本，使 AI 可控落地 | 难证明治理投入的业务回报；担心又建一个平台 | 用案例周期、返工、风险和结果形成可测闭环；叠加既有系统 |
| 项目 Sponsor：数据平台/分析负责人、业务运营负责人 | 推动一个明确场景完成并被采用 | 缺 Owner、优先级和跨部门配合 | Agent 拆分微任务、追责和升级；案例全貌可见 |
| 业务 Owner / 主题专家 | 保证定义符合真实业务 | 不愿学习复杂治理工具；担心被技术字段绑架 | 只接收与自己相关的最小任务、对比和决策材料 |
| Data Steward / 数据产品经理 | 维护术语、指标、规则和流程 | 人工催办、证据不完整、变更难追溯 | 自动发现缺口、整合争议、维护契约生命周期 |
| 数据工程师 / 分析师 / 模型团队 | 获得可执行、稳定、可测试的定义 | 需求反复变化，责任落到实现人员 | 明确的版本、映射、影响、测试和生效边界 |
| 安全、合规、审计 | 确认数据用途、权限和决策可追溯 | Agent 权限过大、输入泄露、审计断点 | 人工授权、最小权限、策略门、审计事件和回滚证据 |
| 系统 Owner / 发布人 | 安全更新下游平台 | 多系统不一致、回滚困难 | 适配器预览、受控发布、目标级状态与回滚点 |
| 咨询、FDE、系统集成伙伴 | 更快交付治理或 AI 落地项目 | 项目知识难复用、定制协调成本高 | 可复用案例模板、契约和集成边界；保留客户控制权 |

购买者、使用者、批准者不是同一个人。产品必须把这类多边关系作为基础模型，而不是把所有权限压成“管理员/成员”两级。

## 5. Jobs to Be Done

### 5.1 组织级主任务

当一个关键业务定义需要新增、澄清或改变时，组织希望在不依赖反复人肉协调的前提下：

1. 看见当前口径、实现、负责人、使用方和历史；
2. 找出冲突、缺失证据和受影响对象；
3. 让正确的人只完成自己有权且最擅长的判断；
4. 对候选定义的业务与技术影响形成共同视图；
5. 以明确授权批准一个有范围、有时间的版本；
6. 安全地同步到既有系统并保留回滚；
7. 从真实使用和业务结果判断是否需要再次修订。

### 5.2 角色级任务

- 业务 Owner：“不要让我读完整数据模型；告诉我具体冲突、证据和要我决定的边界。”
- Data Steward：“不要再手工追十个人；让我看见哪些缺口阻塞生效、谁负责、是否超时。”
- 数据工程师：“不要给我一句口径描述；给我稳定版本、输入、边界、映射、测试和生效时间。”
- 合规人员：“不要让我事后查聊天记录；让我在发布前看见用途、数据、授权、例外和审计链。”
- 管理者：“不要只报告录入了多少术语；告诉我定义变化是否更快、更少返工、更少造成错误动作。”

## 6. 产品对象与产品形态

### 6.1 核心对象

| 对象 | 作用 |
|---|---|
| Definition Change Case | 一次从触发到观察/关闭的定义变化，是工作和审计的主容器 |
| Business Definition Contract | 被批准的机器可验证定义版本，包含语义、责任、范围、时间、映射和控制 |
| Evidence | 支持、反驳或限制候选定义的来源及摘要，带新鲜度和权限边界 |
| Candidate / Dispute | 候选口径、差异、反例、异议、处理结论及保留意见 |
| Human Microtask | 交给特定角色的最小请求，包含上下文、权限、截止和完成标准 |
| Impact | 受影响的指标、字段、报表、模型、Agent、流程、用户和政策 |
| Release | 某契约版本到某目标系统的预览、批准、执行、验证和回滚记录 |
| Outcome Signal | 使用、质量、异常、业务结果和人工反馈，不自动等同因果结论 |

### 6.2 候选界面

具体信息架构尚未通过人类架构/产品讨论，以下只定义必要任务面：

- **Change Inbox**：待处理案例、阻塞、超时、升级和高风险动作；
- **Case Map**：目标、证据、人员、候选、争议、影响和状态的可解释关系；
- **Microtask Surface**：无需理解全系统即可完成补证、确认、异议或审批；
- **Definition Compare**：旧版/候选版的语义、范围、时间和下游差异；
- **Impact & Simulation**：受影响对象、样本摘要、测试与不确定性；
- **Contract Registry**：已批准版本、有效期、映射、Owner、历史和引用；
- **Release Control**：目标级预览、授权、执行、验证、失败和回滚；
- **Observation Loop**：采用、异常和业务信号，触发复审但不自动改定义。

Agent 可通过 Web、企业 IM/邮件、API、MCP 或嵌入式任务入口交接工作。先支持哪个渠道是架构和试点决策，不在本文件冻结。

### 6.3 产品形态假设

早期更可能是“软件 + FDE/咨询式落地”的 B2B 试点：

- 产品提供案例、契约、Agent 协作和审计核心；
- 适配器连接客户已有目录、指标、工单、IM、数据与身份系统；
- FDE 与客户共同建立首个案例、权限边界和成功基线；
- 重复出现的模式才进入标准模板或连接器。

这不是长期服务模式的承诺。应跟踪每次试点中不可复用的人工工作，防止产品退化为定制咨询。

## 7. Agent 与人的责任边界

### Agent 可以

- 在授权范围内发现和摘要证据；
- 标记冲突、缺失、新鲜度和影响候选；
- 生成可解释的定义候选和反例；
- 提议责任人、微任务、依赖和截止时间；
- 追踪、提醒、升级或根据新证据重排未执行任务；
- 生成契约草案、测试计划、发布预览和结果摘要；
- 在预先授权、可回滚的低风险目标上执行受控动作。

### Agent 不可以

- 把概率性输出伪装为企业事实；
- 替无授权的人完成业务裁决、例外接受或高风险发布；
- 为了完成流程而隐藏来源缺失、争议、过期或权限不足；
- 将一个范围内的定义默认扩展到全组织；
- 在未明确策略与用途时向外部模型发送敏感原文；
- 把相关性或发布后变化直接宣称为定义变更造成的业务因果。

## 8. 品牌架构候选

### 8.1 名称关系

| 名称 | 候选角色 | 使用边界 |
|---|---|---|
| **数契** | 中文主品牌/产品名 | 中国市场、产品界面、客户沟通；表达“数据/业务定义之间可追溯的约定” |
| **ContextOx** | 英文主品牌及国际名称 | 域名、英文产品、代码空间或跨境沟通；表达 context + 稳健执行意象 |
| **AlphaOx** | 历史项目名/工程代号 | 保留代码与历史文档追溯；不建议继续作为对外产品品牌 |

此表是品牌提案，不授权仓库、包名、域名、法律实体、商标或 UI 重命名。

### 8.2 为什么是“数契”

“数”不只指数据行，也指业务对象、指标、规则和它们的系统映射；“契”强调的是有主体、有范围、有依据、有时间、有履行与追溯的约定。

它不能被解释为区块链合约、法律合同或自动执行一切的智能合约。对外文案应紧接产品定义，避免单独使用造成误解。

### 8.3 为什么保留 ContextOx

Context 表达 Agent 做出可靠动作所需的组织上下文；Ox 表达稳健、负重和长期运行，而不是追求无约束自动化。该解释是品牌叙事，不应变成性能或可靠性承诺。

## 9. 品牌信念与叙事

### 9.1 核心信念

1. **企业定义不是提示词附录，而是核心数据资产。**
2. **好的 Agent 不是替人拍板，而是让正确的人在正确时刻做最小且有依据的决定。**
3. **变化不是治理失败；无法解释、发布、追溯和学习的变化才是。**
4. **自动化必须服从授权、证据、时间和回滚。**
5. **治理价值最终要回到业务使用和结果，而不是术语数量。**

### 9.2 叙事结构

1. 企业正在让 Agent 更深地进入分析和运营；
2. 但 Agent 假定的业务定义往往分散、冲突并持续变化；
3. 结果是错误口径被更快地复制到更多系统；
4. 数契把一次定义变化组织成 Agent 与人共同完成的受控案例；
5. 最终形成可执行、可追溯、可回滚并能从结果学习的业务定义契约。

### 9.3 候选价值主张

对管理者：

> 让跨部门定义变化从反复协调，变成可测、可控、可复用的组织流程。

对数据与治理团队：

> Agent 主动找证据、找人和追缺口；你保留业务决定与发布控制。

对 AI/数据平台团队：

> 给每个 Agent 和下游系统同一份有版本、有范围、有时效的业务定义。

这些文案必须在真实访谈中测试理解度和可信度，不能直接作为已验证宣传语。

## 10. 语言原则

### 应该使用

- “提议、标记、请求确认、受控发布、可回滚、可追溯”；
- “公开资料显示”“当前假设”“需要演示/试点验证”；
- “有权人最终批准”“在授权范围内”；
- 具体对象和行为：定义版本、证据、微任务、影响、有效期、发布目标；
- 可验证结果：周期、返工、遗漏、未授权动作、采用和异常。

### 避免使用

- “自动理解企业所有业务”“零配置”“一次接入全部治理”；
- “取代数据治理团队/目录/指标平台”；
- “唯一”“首个”“没有竞品”这类无证据排他表述；
- 把“AI 建议”写成“事实”，把“相关结果”写成“因果收益”；
- 空泛的“数据智能底座”“企业大脑”“全生命周期闭环”而不说明对象和边界；
- 把权限不足、数据过期或部分失败包装成成功。

## 11. 产品原则

| 原则 | 可观察行为 |
|---|---|
| Evidence before confidence | 候选定义显示来源、时间、缺口和反例；没有证据时明确停下 |
| Human authority is explicit | 每个决定和动作标识谁有权、依据什么授权、能否委托 |
| Change is first-class | 任何定义都有版本、差异、原因、有效区间和迁移/回滚边界 |
| Minimum human burden | 每个人只收到完成决策所需的最小上下文和最小任务 |
| Integrate before replace | 先连接目录、指标、协作和策略系统；不要求客户重建数据栈 |
| Fail closed | 权限、证据、时效、策略或目标状态未知时，不声称完成、不静默发布 |
| Outcome without false causality | 记录采用和结果信号，同时保留混杂因素和验证方法 |
| Audit by construction | 审计来自领域事件和控制面，不依赖事后拼接聊天日志 |

## 12. 非目标与品牌护栏

- 不是消费者 AI 助手；
- 不是通用聊天机器人或 BI Copilot；
- 不是新的全栈数据平台；
- 不是用 AI 自动写满数据目录；
- 不是僵化所有业务变化的数据标准官僚系统；
- 不是绕开业务 Owner 的技术治理工具；
- 不是把客户数据集中复制到不可控模型的托管知识库；
- 不是以“Agent 自治”为理由取消审批、审计和回滚。
