## 1. 结论先行

ContextOx 不应再被定义为一个更会问答的 ChatBI，也不应声称“市场上还没有 Agent 推动的数据治理”。公开资料已经显示，Atlan、DataHub、Collibra、Ataccama、阿里云 DataWorks 等产品覆盖了 AI 建议、业务上下文、任务与审批、规则执行、审计或持续治理闭环中的一部分。

当前值得验证的更窄切口是：

> **以“业务定义变更案例”为第一等对象，由 Agent 发现缺口、拆分并追踪跨角色微任务，把证据、争议、影响、决策、双时间版本、下游发布和结果反馈收束为可审计的业务定义契约。**

这一定位是产品假设，不是已经证实的市场空白。尤其是竞品的私有功能、交付项目能力和路线图无法从公开资料穷尽，所有“未见”结论都必须通过演示、RFP、客户访谈或试点验证。

## 2. 证据标记

| 标记 | 含义 | 使用规则 |
|---|---|---|
| `PUBLIC FACT` | 厂商官方文档、官方产品页或开源仓库明确披露 | 只能复述其公开能力，不把营销表述当成独立验证 |
| `INFERENCE` | 基于公开材料和当前产品目标的推断 | 必须写明推理边界，不得表述为竞品缺失或客户需求事实 |
| `DEMO NEEDED` | 公开资料不足以确认的能力、边界或商业条件 | 进入竞品演示、RFP、客户访谈或试点清单 |
| `PRODUCT HYPOTHESIS` | ContextOx 的目标用户、价值或产品选择 | 需要通过发现访谈和付费试点证伪或确认 |

## 3. 问题定义

### 3.1 真实问题

企业的数据 Agent、BI、指标平台和自动化工作流，常把下面这些条件当作已经成立：

- 字段、指标和业务对象有稳定、唯一且被共同理解的定义；
- 业务口径变化会及时映射到技术实现；
- 例外、有效期、负责人和审批关系是可发现的；
- 不同系统中的同一概念可以追溯到同一决策；
- Agent 遇到定义缺口时知道该找谁、问什么、何时停止；
- 变更发布后有人验证它是否改善了业务结果。

现实中，定义散落在会议、群聊、工单、SQL、报表、文档和人的记忆里。问题不是只有“没有元数据”，而是定义的形成与变更缺少一个可执行、可追责、可回滚的协作过程。

### 3.2 具体例子：高潜客户

销售负责人提出：“把高潜客户名单更新一下。”

同一句话可能同时包含：

- 销售按近 30 天收入和预计成交概率理解；
- 市场按行为分、公司规模和活动响应理解；
- 财务要求排除逾期或信用受限客户；
- 合规要求某些地区或数据用途不得进入模型；
- 数据团队发现 CRM、计费和产品事件中的客户主键并不一致；
- 旧口径仍被三个报表、两个自动化触达和一个模型使用。

ChatBI 可以生成查询，但不能替企业决定哪种定义有权生效。传统目录可以记录术语，却未必主动推进缺失决策。ContextOx 的候选职责是把这次变化转成一个 Definition Change Case：找证据、找人、收集分歧、模拟影响、形成契约、受控发布，再观察结果。

## 4. 资产观：企业经验不是对话残留物

ContextOx 将以下对象视为企业可治理资产：

- 定义：业务术语、指标、分群、规则、资格条件；
- 证据：数据样本摘要、制度、合同、历史决策、系统实现和负责人陈述；
- 争议：候选口径、反例、未解决问题和否决理由；
- 映射：业务定义到字段、指标、SQL、模型、API、报表和流程的关系；
- 时间：何时被记录、何时对业务生效、何时失效；
- 例外：适用范围、豁免、临时规则和风险接受；
- 决策：提出人、审阅人、批准人、授权边界和依据；
- 结果：发布后的采用、质量、业务效果、异常和回滚。

核心不是积累更多文本，而是将这些对象组合成可验证、可执行和可追溯的 **Business Definition Contract（业务定义契约）**。

## 5. L1–L5 能力分层

能力层级用于比较问题覆盖面，不代表成熟度评分，也不意味着每个厂商只能处于一层。

| 层级 | 核心问题 | 典型能力 | ContextOx 候选职责 |
|---|---|---|---|
| L1 发现与盘点 | 现在有什么、在哪里、由谁负责 | 元数据扫描、目录、血缘、质量、Owner、现有术语与实现发现 | 连接现有目录/仓库，不重建通用扫描平台；形成变更案例的证据入口 |
| L2 提议与建模 | 定义可能是什么、缺什么证据 | AI 描述、分类、术语/指标/规则候选、冲突与缺口检测 | 生成带来源和不确定性的定义候选、利益相关方图和待办微任务 |
| L3 治理与决策 | 谁参与、如何达成可追责决定 | 评论、任务、审批、权限、状态、版本、政策、审计 | Agent 自适应交接；争议记录；职责、委托、超时和人工最终裁决 |
| L4 影响与发布 | 变更会影响什么、如何安全生效 | 影响分析、测试、编译/部署、访问控制、分阶段发布、回滚 | 双时间契约；多目标适配器；发布前预览、回归检查、受控生效和回滚 |
| L5 学习与演进 | 发布后是否有效、何时需要再次改变 | 使用与结果反馈、异常、漂移、持续观察、下一轮建议 | 将业务结果、例外和执行轨迹连接回原案例，触发复审而不自动改写真相 |

ContextOx 的目标覆盖面是 L2–L5，并通过适配器复用 L1。该边界仍需产品访谈和架构决策门确认。

### 6.4 竞争结论

1. **已被证伪的说法**：市场没有 Agent 推动的数据治理、没有人工审批闭环、没有持续上下文或影响分析。
2. **仍可成立的假设**：多数产品从数据资产、目录、规则或平台出发；ContextOx 可尝试从“一次业务定义为何、由谁、依据什么发生变化”出发。
3. **尚未证明的空白**：自适应跨角色微任务、双时间业务定义、多平台编译发布、业务结果回流是否能组成客户愿意付费的独立品类。
4. **真正的竞争对象**：不仅是软件，还包括现有数据治理流程、咨询/FDE 项目、飞书/钉钉/邮件人工协调、内部工单系统，以及“先不治理”的组织选择。

## 7. 候选差异化：定义形成与变更控制层

### 7.1 第一等对象

ContextOx 的第一等对象不是表、字段、Dashboard 或聊天会话，而是 **Definition Change Case**。每个案例至少回答：

- 为什么现在要改变；
- 哪些事实、系统和人受影响；
- 哪些信息已知、冲突、缺失或过期；
- 谁能提出、审阅、批准、否决、执行和回滚；
- 哪个版本在什么业务时间和记录时间有效；
- 如何映射并发布到下游；
- 发布后用什么信号判断有效、失效或需要复审。

### 7.2 Agent-native 协作

候选流程不是让人先画固定低代码流程，再让 Agent 填空；而是：

1. Agent 从目标和现有证据生成可解释的案例图；
2. Agent 只把最小、角色匹配的微任务交给对应人员；
3. 人完成自己的判断、补充证据或审批后把控制权交还 Agent；
4. Agent 根据新证据重算缺口和影响，必要时追加、取消或升级任务；
5. 未满足授权、证据、时效或安全条件时 fail closed；
6. 最终业务裁决和高风险发布仍由有权人完成。

固定流程模板仍可作为政策护栏和可重复起点，但不应成为唯一运行模型。

### 7.3 双时间与多目标发布

同一版本至少需要区分：

- `recorded_at`：系统何时记录这个事实或决定；
- `effective_from` / `effective_to`：定义何时对业务生效；
- `published_at`：何时下发到某个目标系统；
- `observed_at`：结果或异常何时被观察。

批准的契约应通过适配器编译到术语表、指标层、数据契约、策略引擎、报表说明或 Agent 上下文，而不是要求企业先替换所有既有平台。多目标发布是候选方向，具体支持范围必须通过架构决策门批准。

## 8. Business Definition Contract 最小结构

| 分区 | 最小字段 |
|---|---|
| 身份 | 稳定 ID、名称、类型、领域、状态、版本 |
| 语义 | 正式定义、包含/排除条件、边界、示例与反例 |
| 依据 | 来源、证据摘要、置信度、未解决问题 |
| 责任 | Owner、提出人、审阅人、批准人、执行人及委托关系 |
| 适用性 | 组织、地区、产品、渠道、客户段、例外和政策约束 |
| 时间 | 记录时间、业务生效区间、发布与观察时间 |
| 映射 | 字段、指标、SQL、模型、API、报表、流程和上/下游依赖 |
| 变更 | 变更原因、候选差异、影响、审批、发布计划和回滚点 |
| 结果 | 采用情况、质量/业务信号、异常、反馈和下一次复审条件 |
| 审计 | 不可抵赖的事件、主体、权限依据、输入/输出摘要和追踪 ID |

它不是另一份静态文档；其结构和生命周期应能被机器验证。具体 Schema、签名、存储和互操作格式尚未批准。

## 9. 市场进入假设

### 9.1 优先 B2B，不做 B2C

`PRODUCT HYPOTHESIS`：首批客户应是已有数据平台或治理基础、但跨部门定义变更成本高的中国中大型组织，包括：

- 数据成熟度较高的中大型互联网和科技企业；
- 金融、制造、能源、零售等受监管或多业务线企业；
- 通过关系和项目制进入的国企、政府及大型传统组织；
- 需要把现有治理平台、指标平台和 Agent 连接起来的咨询/FDE 伙伴。

早期 SMB、个人用户和自助式 B2C 不优先：它们往往缺少正式 Owner、审批链和稳定系统边界，业务变化速度也可能高于契约化收益。这个判断仍需访谈验证，不能推广为所有 SMB 都不需要标准化。

### 9.2 首个商业形态

候选形态是高接触的付费发现与试点，而非立即做通用自助 SaaS：

- 选择一个高频、高争议、可量化结果的定义案例；
- 接入最少的现有系统和角色；
- 与客户共同建立基线和成功标准；
- 跑完一次完整变更、受控发布和结果观察；
- 证明可重复性后再产品化模板和连接器。

中国优先不等于中国专属。英文品牌和供应商中立的契约/适配器可为后续海外验证保留空间，但当前不应直接正面替换 Atlan、Collibra 等全球全栈平台。

## 10. 明确非目标

- 不替客户自动决定有争议的业务真相；
- 不以 ChatBI 或自然语言生成 SQL 作为首要产品入口；
- 不从零重建通用数据目录、血缘扫描、主数据、BI、湖仓或 IAM；
- 不承诺一个 Agent 自动修复所有数据治理问题；
- 不把未审阅的模型输出直接写入生产定义或下游系统；
- 不以关系图、低代码画布或聊天 UI 本身作为差异化；
- 不在没有客户证据前宣称形成了新品类或唯一市场空白。

## 11. 需要验证的决策门

| 决策门 | 当前状态 | 最少证据 |
|---|---|---|
| 类别名称是否使用“业务定义运营/变更控制” | `PENDING` | 10–15 个目标客户访谈中能被无提示复述，且不被误解为传统目录或 ChatBI |
| 首个 ICP 是否聚焦中国中大型企业 | `PENDING` | 至少三个不同类型组织的痛点、预算、Owner 和采购路径证据 |
| 高潜客户是否适合作为首个场景 | `PENDING` | 找到真实案例、现有周期/返工基线、可接入系统和授权试点团队 |
| Agent 微任务模式是否优于固定工作流 | `PENDING` | 同案例对照：减少无效交接，同时不降低审计、可预测性与控制 |
| 双时间契约是否是刚需 | `PENDING` | 客户存在追溯、未来生效、回填或并行口径的真实损失案例 |
| 多系统编译发布是否构成独立价值 | `PENDING` | 至少两个下游目标的真实一致性成本和受控发布需求 |
| 产品是独立平台还是现有治理平台叠加层 | `PENDING ARCHITECTURE / PRODUCT GATE` | 竞品演示、集成约束、部署与安全要求、试点成本比较 |

## 13. 当前结论的失效条件

出现以下任一证据时，应重新评估定位，而不是继续维护既有叙事：

- 目标客户并不把定义变更视为独立预算问题；
- 成熟治理平台已能低成本完成同样的跨角色、双时间、多目标和反馈闭环；
- 客户无法或不愿授予 Agent 所需的元数据、协作或发布权限；
- 人工协调成本无法形成可测基线，或 Agent 微任务反而增加认知负担；
- 高潜客户场景无法在不处理大量主数据和组织政治的前提下形成小型试点；
- 多系统契约无法维持供应商中立，最终退化为定制集成项目。
