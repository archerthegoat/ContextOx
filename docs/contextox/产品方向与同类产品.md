# ContextOx / 数契：产品方向与同类产品观察

> 状态：产品方向草案，不是架构决策、开发路径图或商标结论
> as_of: 2026-08-29
> 当前用途：作为下一轮产品与架构讨论的输入

## 1. 工作名称与产品定位

- 英文工作名：**ContextOx**
- 中文工作名：**数契**
- 暂定品类：**Business Semantics Agent / 业务语义治理 Agent**
- 一句话定位：**ContextOx 把不断变化的业务口径，持续转化为可验证、可执行、可追溯的数据契约。**

ContextOx 不是先做一个直接回答业务问题的 ChatBI，也不是假设企业已经拥有完美数据库、完备字段说明和稳定指标口径。它先解决 ChatBI 与 Data Agent 的上游问题：推动业务方、数据团队和使用方共同补齐定义，处理分歧与例外，把确认后的口径映射到真实数据，并在业务条件变化时重新进入变更流程。

这里的 Agent 负责发现缺口、收集证据、组织协作、生成候选方案、模拟影响和执行已批准的变更；业务定义的最终批准权仍属于人。

## 2. 核心问题

现有 ChatBI、语义层和 Data Agent 通常需要先具备以下条件：

- 字段含义明确，表与字段之间的关系可信；
- 指标、维度、过滤条件和时间口径已经定义；
- 业务词汇在部门之间基本一致；
- 定义能够映射到可查询的数据；
- 数据质量、权限和更新时效达到可用标准。

但生产环境里的真实状态往往相反：业务人员知道意图却难以写成规范，技术人员能落 SQL 却未必理解业务判断；同一个词在不同部门、地区、产品和时间段可能含义不同；临时活动、政策变化和经营目标又会持续修改阈值、范围和例外。

所以最难的不是再生成一次 SQL，而是完成以下闭环：

1. 把模糊业务意图转化为待确认的问题；
2. 找到相关定义、数据、责任人、使用方和历史变更；
3. 形成可比较的候选口径并评估影响；
4. 由授权人员批准、驳回或修改；
5. 将批准结果编译为机器可执行规则；
6. 持续观察结果、例外和业务变化，再触发下一次修订。

## 3. 企业真正需要积累的数据资产

> 企业长期积累的业务概念、判断规则、适用条件、例外、历史变更、结果反馈，以及这些知识与真实数据之间经过验证的映射。

本项目的核心假设是：企业难以复制的资产不只是原始数据量，而是上述知识、证据和数据映射形成的长期记忆。模型能力会继续普及，但一家公司为什么这样判断、什么时候不能这样判断、过去如何修改、修改后产生了什么结果，这些上下文不会自动存在于通用模型中。

因此，ContextOx 应沉淀的不是一份静态术语表，而是可追溯的业务定义网络：定义之间有关联，定义与数据有映射，变更有生效时间与审批证据，执行结果又会反向补充下一版定义。

## 4. 首个代表性场景：圈定高潜客户

### 4.1 为什么选这个场景

“高潜客户”表面上像一个筛选条件，实际通常包含多个未决问题：高潜针对什么目标，观察窗口多长，使用收入、活跃度、增长率还是销售判断，阈值是否随活动和地区变化，新客户如何处理，黑名单和合规限制如何排除，以及名单最终由谁使用。

它同时具备业务价值、跨部门协作、动态口径、真实数据映射、影响可计算和结果可反馈等特征，适合作为 ContextOx 的第一条端到端验证链路。

### 4.2 Agent 推进流程

1. **接收业务意图**
   记录目标、使用场景、期望时间、调用方和当前口头描述，不把一句自然语言直接当作正式定义。

2. **识别缺口与冲突**
   检索现有指标、字段、历史名单、会议纪要、活动规则和查询；列出缺失条件、同名异义、互相冲突的版本和无法验证的假设。

3. **确定责任与审批路径**
   识别业务负责人、数据负责人、合规或风控负责人、最终名单使用方，以及谁有权批准正式口径。

4. **生成候选定义**
   根据目标和证据生成少量可执行方案。每个方案必须明确人群范围、排除项、指标、窗口、阈值、生效时间、数据来源、未知项和置信边界。

5. **执行影响模拟**
   在只读环境中比较候选方案的人数、重叠率、历史命中、数据覆盖、缺失值、部门或地区分布、下游成本和潜在异常。模拟结果是决策证据，不是自动批准理由。

6. **组织人工决策**
   把分歧、证据和影响发送给对应责任人。人可以批准、修改、驳回或要求补充证据；Agent 不得替业务负责人发明并发布定义。

7. **发布版本化业务定义契约**
   将批准内容登记为一个带版本、生效区间、责任人、证据、数据映射和回滚点的 Business Definition Contract（业务定义契约）。

8. **编译到执行系统**
   通过受控适配器生成或更新 SQL、指标、标签、分群规则、语义模型和其他 Agent 上下文；发布前运行契约校验和影响检查。

9. **观察结果并重新开启变更**
   追踪名单使用结果、误判、人工例外、数据漂移和业务反馈。当阈值、目标或数据条件失效时，创建新变更，而不是覆盖历史定义。

### 4.3 最小业务定义契约

本稿中的 Business Definition Contract 首先是业务定义及其决策证据的契约，不等同于只约束 schema、质量或 SLA 的传统 data contract；批准后，它可以继续编译为下游系统使用的数据契约和执行规则。

首版契约至少需要记录：

- 业务目的与决策场景；
- 适用组织、产品、地区、渠道和时间范围；
- 目标总体、纳入条件、排除条件与例外；
- 指标算法、观察窗口、阈值及阈值依据；
- `effective_from`、`effective_to` 和当前状态；
- 业务 Owner、数据 Owner、审批人和使用方；
- 来源表、字段、转换逻辑与映射版本；
- 数据质量、覆盖率、时效和已知缺口；
- 变更前后的影响模拟；
- 下游消费者、依赖项和发布目标；
- 争议、补充证据、决策记录和结果反馈；
- 版本、前序版本、回滚条件和回滚目标。

## 6. 当前差异化假设

这些内容是下一轮访谈和原型需要证伪的假设，不是已经成立的竞争结论。

1. **治理对象不同**
   不是先治理表、字段或 BI 模型，而是治理“一个业务判断如何变成可执行定义，以及它为什么、何时、由谁发生变化”。

2. **从缺口开始，而不是从完备语义开始**
   产品首先发现定义缺口、冲突、缺少的责任人和证据，再推动形成最低可用契约。

3. **变更是第一等对象**
   每个定义具有业务生效时间、系统记录时间、版本、审批证据、影响范围与回滚关系，不能用覆盖式编辑丢失历史。

4. **先模拟，后批准，再执行**
   候选定义必须能在真实数据上进行只读影响模拟；Agent 不能因为文本看似合理就自动发布。

5. **同一契约可编译到多个消费者**
   已批准定义可以被转换为 SQL、指标、标签、分群、语义模型和 Agent 上下文，而不是在每个工具内重新手工定义一次。

6. **结果反馈进入下一版定义**
   误判、例外、业务结果、漂移与人工修订都成为下一次变更的证据，逐步形成企业自己的业务判断资产。

## 7. 产品边界与安全原则

- Agent 可以提出候选定义，不能自行成为业务定义的最终责任人。
- 没有足够证据、数据覆盖或授权审批时，应保持 `blocked` 或草案状态，不得伪造确定性。
- 原始数据、业务知识、审批权限和执行权限应分别授权，不能因能搜索文档就自动获得写库权限。
- 对 SQL、标签、指标或语义模型的写入必须支持预览、测试、审计、幂等、回滚和失败隔离。
- 历史版本必须保留；“当前有效”不等于“历史上一直有效”。
- 数据质量问题与业务定义问题需要分别标记：数据不符合定义，不代表定义错误；定义发生变化，也不代表历史数据错误。

## 8. 名称结论（当前阶段）

- **ContextOx**：保留为英文工作名，强调 Agent 处理的是企业上下文，而不只是数据本身。
- **数契**：保留为中文工作名，强调业务语义最终形成带责任、证据、版本和执行映射的契约。
- **DataOx**：已有同名数据服务公司，当前不作为首选。
- 上述结论不包含商标、公司名、域名、应用商店或社交账号的完整可用性核验。正式命名前必须另做法律与市场检索。

## 9. 下一轮架构讨论必须回答的问题

1. ContextOx 的首个用户到底是谁：业务负责人、数据治理人员、分析师，还是连接这些人的 FDE？
2. 产品的最小闭环是“生成定义提案”，还是必须完成批准、编译、发布与反馈回收？
3. Business Definition Contract 的权威存储在哪里，如何与现有数据目录、Git、工单和 BI 平台协作？
4. 如何同时表达业务生效时间和系统记录时间，避免用新口径错误解释历史结果？
5. Agent 能读什么、能提议什么、能执行什么；哪些动作必须由哪类人批准？
6. 首批编译目标只支持一种数据栈，还是从一开始定义可扩展适配器边界？
7. 影响模拟需要哪些最低数据质量与隐私条件，数据不足时如何失败关闭？
8. 如何验证“高潜客户”闭环确实减少协作成本，同时没有制造更多形式化负担？
9. 哪些功能应该复用 Atlan、DataHub、SageMaker Catalog 等现有系统，哪些才是 ContextOx 必须拥有的核心？
10. AlphaOx 现有架构哪些可以保留，哪些必须迁移、冻结或废弃；迁移和回滚边界是什么？

这些问题需要由人与主 Agent 共同完成讨论和取舍。在架构报告及完整验收清单获得明确批准前，不进入大规模实现，也不自动修改 `开发路径图.md`。
