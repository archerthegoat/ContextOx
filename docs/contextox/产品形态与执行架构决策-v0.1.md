## 1. 产品结论：从零建立规范，再持续演进

数契是一个从组织目标和全局影响出发，设计、建立并持续演进业务规范的执行 Agent。人给出模糊业务目标后，即使没有现成规范，它也应自主理解业务背景、识别约束、设计规范结构与候选方案、查证和协调补证、准备业务裁决，最终形成可执行、可追溯、可复用的规范契约。已有规范的澄清与修订是后续演进场景，不是启动前提。

人提供目标、必要事实与授权，保留业务裁决、例外接受和高风险发布权；不负责逐步点击推动 Agent。“从零”是没有现成适用规范，不是没有业务事实、边界和责任，也不是让模型凭空制定正确规则。

| 责任 | 承担者 | 具体例子 |
|---|---|---|
| 设计方案并持续推进 | Agent + Mission 执行控制 | 从“建立高潜客户识别规范”出发，设计规则结构、查证约束、提出候选阈值和所需补证 |
| 判断动作是否允许、保存真实状态 | 确定性领域规则与能力边界 | 校验身份、范围、预算、版本和幂等；新规范也不能绕过已有上位约束 |
| 选择方案、裁决争议、批准效果 | 有权人 | 决定识别标准、例外和责任分工，批准明确草案；发布仍另行授权 |

商业入口保留专业用户自助发起、共 2–5 人参与一个限定业务域的验证方向。C 端化的是上手和反馈；共享规范、责任与受控落地是组织价值。纯个人付费、买方、定价和规模化实施仍未被证明。

### 1.1 “规范”不止一个名词定义

首份规范应按场景明确下面这些内容；不能把填满所有栏目当成质量，也不能在缺少证据时伪造完整性。

| 内容 | 需要回答的问题 |
|---|---|
| 业务目标与适用范围 | 为什么制定，适用于谁、什么业务域，不适用于哪里 |
| 对象、定义与判定规则 | 关键对象是什么，如何判断，时间窗口和依据是什么 |
| 职责与协作规则 | 谁提供事实、谁执行、谁裁决，如何处理交接与异议 |
| 约束与例外 | 哪些约束不可违反，例外由谁接受、在何范围有效 |
| 数据/流程映射 | 规则怎样落到已授权的字段、指标、分群或业务动作 |
| 验证与演进方式 | 用什么例子、反例、检查与观察信号判断是否适用，何时复审 |
| 证据、批准与版本 | 每项规则凭什么成立，由谁批准，何时记录和生效 |

Agent 可以提出规范结构和规则方案，但规范性选择必须标为候选，不伪装成来源事实。“可执行契约”意味着结构、规则和映射可被相应能力验证或消费；不意味着首版支持任意业务流程自动部署，也不意味着契约已经发布。

### 1.2 首个七分钟 demo：从模糊目标到首份规范

本次按人类最新反馈，以“从零建立电商高潜客户识别与运营优先级规范”为主场景：哪些已有购买记录的客户值得优先维护，以及规则如何有依据、可验证、可复用。它是电商指标/数据/业务规范的具体案例，不扩成陌生线索或信用评估，不预设旧 Contract。“高潜”是候选运营定义，不自动等于未来购买概率或终身价值。缺少未来购买标签只限制未来预测/效果结论，不自动阻塞当前运营规范；当前事实、目标、约束、权限和业务裁决满足时仍可创建首版。若目标转为预测，需另行确认 Case、证据、评估和授权边界。

最小输入、Olist 来源边界和独立验收设计以 [PRD §5](./PRD-v0.1.md#5-首个场景从零建立电商高潜客户识别规范) 为准，验证包候选细化见 §10.1；原始数据不是公司的目标、政策、责任与授权。Olist 仅有前轮公开说明核对，未下载、导入或通过行级质量验收；自有 fixture、获授权真实数据与模拟任务分别标注。开发路径图的对应精确 diff 已批准并写入，证据见 13.4。

使用 3–4 类 fixture 或获授权的只读来源，展示：

1. 人给出业务目标，Mission 明确范围、权限、预算和成功条件；没有旧 Contract 也可合法启动。
2. Agent 查证客户与订单粒度、支付聚合、时间可用性、运营目标、责任与既有约束；不能把索引没找到误写成“公司没有规则”，也不能把订单级 ID 当独立客户。
3. Agent 设计客户识别规则及候选方案，展示纳入、排除、资料不足与候选差异；说明证据、取舍和待裁决问题，不复述预设分类名单，也不把历史消费直接宣称为未来潜力。
4. 对资料缺口、冲突和待确认责任创建受控补证任务；有效回应到达后自动恢复、更新方案。
5. 用样例、反例和只读影响说明准备核心业务裁决；批准绑定到明确草案、范围、证据与版本。
6. 形成首份 Contract v1、规则与责任说明、验证样例、只读影响说明和发布提案。不伪造 Contract v0 或强制展示“旧版差异”。
7. 用明确标注的 fixture 信号在授权范围提出或创建新关联 Case，保留信号和批准边界；不伪造发布或 OBSERVING 状态。首轮测试旧版绑定与历史保护，完整修订闭环及 v2 交付作为后续独立范围。

“一次核心业务裁决”是演示叙事，不是授权次数上限。身份、数据访问、委托、例外和发布仍各自受控。规范设计、草案与影响说明要在展示前具备，而不是由预设动画替代。

### 1.3 创建与演进是两种输入条件，不是两套产品

| 场景 | 版本和基线 | 展示/交付方式 |
|---|---|---|
| 从零定制 | 允许没有旧 Contract；仍查证相关约束和现有业务实践 | 比较候选方案，形成首个批准版本 v1；历史效果未知就说明未知 |
| 修订已有规范 | 绑定明确旧版本、适用范围及其批准 | 比较旧/新差异与影响，重新批准后形成 v2 或后续版本 |
| 尚不清楚是否存在适用规范 | 记录可见资料、覆盖与缺口，继续查证 | 不把“未找到”自动变成“从零创建”，也不伪造旧版本 |

技术边界继续是 Mission、Case、Agent Run 和 Contract。创建模式不应强制非空的旧规范引用，修订模式应绑定基线；精确字段、基数和模式命名仍待契约门，不在本轮改公共 API 或给类型批量重命名。

一个团队的首份规范可以沉淀为复用候选，但复制到其他团队必须重新核对适用范围、证据、责任与批准。创建、复用、修订和观察属于同一条持续演进链。首轮创建主线只要求创建/修订判别、基线绑定和历史不覆写的保护测试，不把完整修订、旧/新差异工作台或 REVISION PASS 设为首轮交付。

## 3. 来源事实、借鉴与缺口

### 3.1 Zion：执行机制不等于商业验证

2026-08-30 的历史核验来自 Functorz Zion 官方文档：自定义前端或 Runtime API 把输入交给配置好的 Agent，模型选择已授予的工具，再由行为流/API 执行实际动作；身份、权限、参数与副作用控制不能只写在提示词里。相关资料见 [Zion Agent](https://docs.functorz.com/docs/actions/guide/ai_integration/)、[Runtime API](https://docs.functorz.com/docs/developers/runtime_api/) 与 [应用权限](https://docs.functorz.com/docs/publish_operate/permissions/)。

这解释了 C 端体验怎样落到后端动作，不证明数契的个人付费需求。关于“Zion 已赚钱”的具体产品、收入、统计口径与可比业务，本报告没有一手财务证据；不据此推导数契应选择纯 C 或纯 B。本轮未重做 Zion 能力普查。

### 3.2 Uber：借鉴上下文与托管执行，不复制性能结论

## 4. 候选方案与取舍

| 决策项 | 当前方向 | 不作为首选/暂缓的方案 | 理由与代价 |
|---|---|---|---|
| 产品入口 | 专业用户自助 + 小团队协作 | 纯个人工具、全企业治理平台 | 先验证共享定义价值；仍承担协作与责任确认成本 |
| 执行模型 | Mission 持久推进 + 有界 Agent Run | 单次聊天；用户预画固定工作流 | 需要规范设计、查证、等待、恢复和重规划；状态与副作用治理更严格 |
| 模块边界 | 围绕变化原因组织的模块化单体 | 按每个流程阶段拆服务；通用工作流平台 | 减少分布式成本；必须保留小而清晰的模块接口 |
| Web/API | React + Vite、Fastify 候选 | 复用旧聊天界面作为最终产品定义 | 全栈 TS，适合 Mission/任务/契约视图；旧能力须按场景重验 |
| 共享契约 | ContextOx 自有 TypeBox/JSON 契约候选 | 暴露 Pi、工作流引擎或目录内部类型 | 维持领域自主；精确 schema 与版本仍待门 |
| 持久层 | PostgreSQL 当前状态、审计、outbox、可重建索引 | 聊天历史；另起一套图谱真相 | 简化首版运维；仍需隔离表权限、连接池、迁移和备份 |
| 持久执行 | DBOS 优先有界验证 | 自写完整调度引擎；直接引入 Temporal | 先验证足够小的方案；不通过则比较 Temporal 的恢复、运维和退出成本 |
| 检索 | PostgreSQL 实体/关系索引 + 按 Mission 组装 Context Pack | 先上专用图/向量数据库 | 先验证关系是否提高正确性；没有规模证据不增加存储系统 |
| 可视化 | React Flow 候选运行投影；Archify 文档图 | 让用户拖线定义执行逻辑 | 展示实际运行与证据；图本身不拥有批准或执行权 |
| 发布 | demo 只读与提案；路径五单目标沙箱 | 首版任意生产写入、多目标自动扩散 | 保留可控验证路径；沙箱写入同样需要目标级批准 |

DBOS 官方提供无需装饰器的 registerWorkflow 接入，但注明其库与 workflow 不能被普通 JS/TS bundler 打包。因此 Vite 仅用于 Web；服务端构建/运行方案必须在技术验证中独立证明，不能默认把 Worker 一起打包。[DBOS 接入说明](https://docs.dbos.dev/typescript/integrating-dbos)

以上是待验证方案，不是依赖安装清单。精确版本、许可证、来源、安装脚本、依赖树、漏洞与运行时兼容性均须供应链门；本轮没有安装或更新它们。

## 6. 领域、模块与运行契约候选

本节是供主 Agent 与人类讨论的完整候选，不冻结字段、接口、枚举或部署。命名表示职责，不自动要求新增 package、服务或抽象层。

### 6.1 核心对象与权威

| 对象 | 最少需要表达 | 不得混淆 |
|---|---|---|
| Mission | 目标、范围、成功条件、授权、预算、Owner、当前判断、唤醒与停止条件 | 不等于一个聊天 Session 或固定阶段列表 |
| Agent Run | 有界输入、Context Pack 引用、工具能力、预算、输出、错误、取消、Trace | 不拥有业务批准权或跨重启任务权威 |
| Case（现候选名 Definition Change Case） | 一次规范从零设计、澄清或修订的目标、方案、证据、责任、任务、影响与决策 | 不强制已有规范；不是工作流引擎执行历史，最终命名待统一 |
| Evidence | 源版本、记录/业务时间、权限、覆盖、支持/反对、未知与新鲜度 | 模型摘要不是源事实 |
| Context Pack | 当前 Mission 所需且可见的事实、候选、冲突、缺口与引用 | 检索命中不等于批准或完整覆盖 |
| Human Microtask | 明确主体、最小问题、所需证据、依赖版本、期限、委托与完成条件 | 通知送达不等于任务完成 |
| Decision | 有权主体、依据、范围、版本、决定时间与有效授权 | 旧批准不能覆盖内容变化 |
| Business Definition Contract | 目标/范围、定义与规则、职责、例外、Owner、证据、时间、映射、验证和批准 | 首份批准版本可为 v1；已批准不等于下游已生效 |
| Impact | 已知与候选影响、输入版本、目标、覆盖、来源与不确定性；创建比较候选方案与可观察现状，修订比较绑定旧版 | 没有旧规范不伪造 diff；只读模拟不等于真实发布效果 |
| Release / Outcome Signal | 逐目标发布与读回；采用、异常、窗口、基线和其他解释 | 单目标成功、相关信号不等于全局成功或因果收益 |

一个 Mission 可以关联多个判断、Run 和任务。首版如何关联一个或多个 Case、如何拆分大目标和限制循环，仍由后续架构门按真实案例确认，不能为了图好看先固化基数。

### 6.2 按职责和变化原因划分模块

| 候选模块 | 拥有的责任 | 小接口与禁止事项 |
|---|---|---|
| 业务工作台与产品 API | 呈现状态、主体上下文、接收命令、返回受权视图 | UI 不推断批准、不写数据库；API 不复制领域规则 |
| 定义与协作领域 | 规范创建/修订的 Case、方案、证据、任务、Decision/Contract 及其状态与版本规则 | 对外暴露命令和结果；不导出第三方内部类型；创建不被旧版必填约束阻塞 |
| Mission 执行控制 | 唤醒、调度判断、Run 预算、等待、恢复、停止和重规划衔接 | 调用领域策略结果，不复制谁可批准/何时批准失效 |
| 业务上下文 | 来源适配、实体关系、权限/新鲜度过滤、Context Pack | 返回有出处和缺口的上下文；索引不改正式契约 |
| 受控能力边界 | 能力目录、参数约束、调用准入、幂等键和动作收据 | 调用领域授权与工具规则；不自建第二套批准状态机 |
| Pi 运行适配 | 模型/工具事件转换、有界运行、取消、未知事件处理 | 不把 Pi Session 当持久业务状态；不扩大工具能力 |
| 持久执行适配 | 引擎注册、等待/信号/计时、恢复与执行版本衔接 | 不解释业务真相；更换引擎不改契约批准含义 |
| 存储与外部适配 | 明确事务、读取、索引重建、连接器与单目标读回 | 表和连接器按所属责任维护，不建立无边界的通用仓储 |

主体校验、工具权限、审计和版本约束可能跨模块，但每条规则只能有清晰的权威实现与调用者。开始时用内聚的功能模块组织定义、协作和发布；只有出现真实变化模式后才细分。执行顺序、文件大小、Agent 上下文窗口都不是拆模块的充分理由。

### 6.3 数据权威、事务与事件

- PostgreSQL 保存领域当前状态、追加式不可变审计记录及事务 outbox。当前状态和相应业务事件应在同一业务事务中落地。
- outbox 是提交后待投递的事件记录，不意味着跨数据库、引擎或外部系统天然存在一个大事务。消费者按事件/动作标识去重，并保留投递与消费证据。
- 上下文实体/关系表和 Web 运行投影是派生状态；丢失后可从授权源与领域记录重建。它们不可直接覆盖正式契约。
- 调度引擎表保存执行检查点和等待，不作为 Contract、Decision 或 Release 的公共读写接口。
- 同一个 PostgreSQL 实例不等于同一权限账号或同一 schema。分别定义领域、索引、调度的访问权、迁移责任、保留和连接池预算。
- 并发批准和 Worker 竞争必须校验预期领域版本、租约/去重或等效机制。具体实现与 SQL schema 待技术门；不能用“最后写入者赢”吞掉冲突。
- 事件流用于通知 UI 更新。连接断开后读取带版本的最新快照，再补所需事件；不能只靠浏览器收到的 SSE 消息判断业务是否成功。

### 6.4 一次可恢复推进的代表性追踪

1. 人提交目标和授权边界；领域模块保存 Mission/Case 输入与审计，事务 outbox 记录唤醒。
2. 执行控制领取可推进工作，核对停止条件、预算、当前版本和等待依赖。
3. 上下文模块组装 Context Pack；证据不足时返回明确缺口，不把“未找到”写成“不存在”。
4. Agent Run 设计规范结构与候选规则，并选择查证、补证、等待、重规划或准备决策等下一步候选；设计提议和来源事实分别标记。
5. 受控能力边界向领域/策略所有者校验身份、范围、版本、预算与参数，再执行允许动作。
6. 结果、原始错误和动作收据通过所属领域接口持久化；新的业务事件决定继续、等待或停止。
7. 人类有效回应、合法定时器或获授权变化事件到达后重新读取状态与上下文，不能沿用旧权限或过期批准。
8. 创建场景批准后形成首份 Contract v1；修订场景绑定旧版形成后续版本，两者均可准备发布提案。高风险效果另走目标级授权与读回；观察可提出复审，不自动修改已批准规范。

这是一个反馈循环，不要求用户预画 SOP，也不声称每个目标都必须按完全相同的阶段走一遍。

### 6.5 业务上下文索引：来源、关系与复用

首版候选使用 PostgreSQL 记录最少的实体与关系：目标、定义、证据、责任主体、任务、Decision、Contract 及下游使用引用。原始来源、正式契约和组织身份仍各自拥有权威。

索引更新需要保留来源标识、版本/哈希、读取时间、业务时间、访问范围、抽取方式及确认状态。确定性映射、人工确认和模型推断分别标记；同名字段或高使用频率不能自动合并实体、指定责任人或确认标准。

Context Pack 按 Mission 的目的与能力范围筛选，并给出支持、反对、冲突、缺口和新鲜度。不向模型倾倒整个资料库；对敏感证据只传必要摘要和可授权引用。关键动作前重新核对权限、依赖版本及可用性。

删除、撤权、源更新与过期要能使索引、缓存、摘要、导出候选和批准依赖失效。若权限传播延迟超过批准的边界，受影响操作暂停；不能为了召回率泄漏标题、关系或对象存在性。

复用分三层：已批准 Contract/规范是业务资产；索引与 Context Pack 是上下文；Skill/模板是执行方法。运行 Trace 可以提出改进候选，但不自动改 Skill、正式规则、适用范围或批准策略。

检索对照必须先固定同一批授权资料与快照、问题、模型和预算，比较证据/责任人正确性、冲突发现、耗时、调用成本与索引维护成本；另测缺失、过期、矛盾、撤权反例。没有结果前不引用 Uber 的 38 秒作为本项目目标或性能承诺。

### 6.6 持久执行的有界验证门

DBOS 是优先验证候选，不是已经通过的选型。官方配置支持独立的系统数据库 schema；实际表权限、迁移与业务 outbox 的交界仍要由本项目验证。[DBOS 配置](https://docs.dbos.dev/typescript/reference/configuration)

单独获得实施授权后，最小验证应覆盖：

| 试验 | 必须证明的现象 | 否定条件 |
|---|---|---|
| 进程退出与重启 | Mission 从可审计检查点继续，已确认领域动作不重复 | 丢状态、重复任务或错误跳过动作 |
| 信号先到/后到、重复与乱序 | 回应绑定任务和版本，能够去重或拒绝无效事件 | 丢失唤醒、旧回应满足新任务 |
| 两个 Worker 与持久计时器 | 同一动作不重复产生业务效果；唤醒范围与预算受控 | 双执行、无限重试或通知风暴 |
| 数据库部分失败 | 区分业务提交、outbox 投递与引擎推进，能够对账 | 某层成功被伪装成整体成功 |
| 模型/工具非确定行为 | 有界输入输出与收据可重用；未知副作用先读回/人工处置 | 恢复时盲目重新调用外部动作 |
| 代码版本升级 | 在途任务有明确兼容、排空或迁移路径 | 新代码错误解释旧执行历史 |
| 引擎退出 | 从领域状态、任务和审计重建可解释的继续点 | 只有供应商内部历史能知道业务进度 |

工作流恢复不能证明外部动作 exactly-once，也不能替代目标级幂等、授权、readback 和补偿。若关键试验不通过，停止固化引擎，带证据比较 Temporal 等替代方案；不在本轮偷偷实现第二套调度器。

### 6.7 用变化场景检查边界

| 真实变化 | 应主要改动 | 需要核对的调用者 | 不应无理由连带改变 |
|---|---|---|---|
| 更换模型/Pi 包版本 | Pi adapter、模型配置和事件转换 | Run 输入输出、取消与预算测试 | 契约批准语义、Case 状态权威 |
| 文档格式或责任目录来源变化 | 来源适配、实体映射与索引更新 | Context Pack 覆盖/权限/新鲜度 | Mission 主循环、UI 裁决逻辑 |
| 批准角色或批准失效条件变化 | 定义协作领域的策略及 Decision 规则 | API/任务投影、能力边界及旧批准处理 | 在 Worker 复制同一规则 |
| DBOS 更换为另一引擎 | 持久执行适配、在途迁移与运维 | 唤醒、计时器、重试和恢复契约 | Business Definition Contract 格式 |
| 更换检索/图存储方案 | 上下文查询与索引实现、重建程序 | 权限过滤、Context Pack 语义和性能 | Agent 被迫消费某数据库内部类型 |
| 从修改已有规范扩展到首份规范 | 定义协作领域的创建输入约束、方案校验与首版生成 | 工作台创建入口、方案对比、影响展示；检查旧版引用是否被无条件必填 | 为创建模式另建一套 Agent、存储或审批平台 |
| 增加一种业务规范类型 | 对应内聚领域功能、校验与模板 | 契约视图、影响/发布适配器按实际需要变化 | 先造一个无限可配置通用引擎 |
| 引入新的沙箱发布目标 | 目标适配器及权限/读回/回滚实现 | Release 状态、影响说明和任务授权 | 重新实现 Case 与批准规则 |

变化跨多个模块并非天然失败。判断标准是每处改动是否有真实职责原因，旧可观察契约是否仍成立，能否通过公共边界上的反例检验；不以文件数量评分。

## 7. 状态、失败与恢复矩阵

下面分开执行、证据、批准与发布状态，避免一个“完成”覆盖所有维度。大写状态名是讨论标签，不是已冻结枚举。

| 维度/事件 | 持久记录与行为 | 用户可见 | 继续条件/禁止事项 |
|---|---|---|---|
| Mission DRAFT/RUNNABLE | 保存目标、范围、授权、预算与当前草案/领域版本 | 待完善或可执行 | 旧 Contract 不存在可合法创建；没有成功条件/授权不能无限探索 |
| NO_APPLICABLE_CONTRACT | 已确认本次范围内无适用旧 Contract，保留相关上位约束与创建依据 | 可创建首版 | 目标、事实、范围与授权等其他创建条件仍须满足；不得伪造 Contract v0 |
| UNCONFIRMED / 检索覆盖不足 / 无权读取 | 保留未知原因及可见范围，继续受限查证、补证或请求授权 | PARTIAL / BLOCKED，不能直接创建 | 普通“继续”不能转成可创建；收窄范围后也需重新确认适用性及全部创建条件 |
| DESIGN_ALTERNATIVES | 保留方案、依据、取舍、样例/反例与待裁决项 | 规范设计中 | 机器提出的规则不标为组织既定政策 |
| Run RUNNING/RETRYABLE | 保留调用、尝试与原因；重试有上限 | 正在查证/重试原因 | 重试不得重复未知副作用 |
| WAITING_HUMAN/EVENT | 去重任务、等待原因、期限和唤醒条件 | 等谁、缺什么、何时复核 | 有效回应后自动恢复，不代签 |
| EVIDENCE_PARTIAL | 逐源覆盖、错误、as_of 与已得证据 | 部分证据 | 影响批准的关键缺口不能被普通“继续”绕过 |
| CONFLICT/STALE | 并列候选、版本与受影响依赖 | 未决争议/过期 | 重新查证或有权人裁决；不能只取最新文件 |
| ACCESS_DENIED | 记录脱敏拒绝；停止受影响检索与动作 | 权限不足 | 不泄漏内容、标题、关系或存在性 |
| BUDGET_EXHAUSTED | 保存已花费、额度和继续所需授权 | 预算耗尽 | 不自动换高价模型或扩大授权 |
| TOOL_OUTCOME_UNKNOWN | 保存请求、幂等键与已知收据 | 动作结果未知 | 先读回/对账，不能把重放当恢复 |
| READY_FOR_DECISION | 草案、证据、影响和依赖版本完整 | 可审阅 | 不等于批准，批准人必须有权 |
| APPROVED | 追加 Decision 并固化 Contract 版本 | 已批准、未发布 | 内容/范围/关键证据变化使相关批准失效 |
| EXPORTED/PROPOSAL_READY | 生成版本化提案与哈希 | 已导出/发布待授权 | 不等于目标已写入 |
| PUBLISH_PENDING | 逐目标 preflight、授权与版本再校验 | 等待某目标发布 | 沙箱与生产分别授权 |
| PUBLISHED_PARTIAL | 保存逐目标结果并停止自动扩散 | 哪些成功、失败或未知 | 不合并成全局 success |
| PUBLISHED_VERIFIED | 目标 readback 与批准版本一致 | 已发布并读回 | HTTP 2xx 或 Worker 结束不够 |
| ROLLBACK_FAILED | 保留原发布、补偿动作、读回与错误 | 回滚失败/需处置 | 不删除历史或声称恢复完成 |
| REJECTED/CANCELLED | 保存理由、取消等待与未来新动作 | 已拒绝/取消 | 取消不抹去已发生外部效果；必要补偿另行批准 |
| REOPEN_PROPOSED | 保存授权观察信号与复审理由 | 建议复审/新 Mission | 不复用旧批准自动改正式规范 |

额外反例必须进入后续测试：无旧规范但目标合法；无权读取却误判为空白；以通用模板冒充已适配规范；已有上位约束与新方案冲突；没有历史数据却编造旧版效果；两位批准者同时提交；Owner 离职/委托撤回；回放旧 webhook；源删除后缓存仍存在；Agent 返回无效 JSON/未知事件；网络断线导致 Web 状态落后；通知失败而任务已创建；模型中断但工具已执行；跨时区期限和未来生效；历史更正、范围重叠和重复任务；观察信号只是相关而非因果。

## 8. 权限、时间、可观测性与可访问性

### 8.1 权限从首版成立

- 最少需要可信主体、工作区/业务范围、任务与工具能力校验。演示可以使用明确标记的 fixture 身份，真实数据必须使用适用的认证与授权。
- 发起、补证、异议、批准、发布、审计可以由不同角色承担；角色映射、职责冲突和委托规则仍待人类确认。
- 每次敏感读取、工具执行、批准、导出和发布都记录主体、授权依据、范围、版本与结果。
- 客户资料是数据，不是 Agent 指令；检索文本不能扩权、替换政策或命令模型外传秘密。
- 秘密保留在服务端受控配置，不能进入 Web、Git、提示词、默认 trace 或工件；日志默认脱敏。
- SSO、SCIM、企业目录与组织级策略可后置；基础身份、最小权限、审计、批准有效性不能后置。

### 8.2 时间和新鲜度

对齐 PRD 的概念：recorded_at 表示系统何时记录；effective_from/effective_to 表示何时对业务有效。证据还需要来源版本、实际读取时间、覆盖窗口与新鲜度；发布需要 readback 时间和目标版本。

旧报告的 observed_at、valid_from/valid_to 只是旧候选用词，不在本轮暗中冻结成另一套公共字段；精确 schema 在契约门统一。未来生效、追溯更正、迟到证据、范围重叠、时区/日历和批准失效必须分别定义。历史记录不原地覆盖。

### 8.3 可观测性和成本

在受控日志中串联 Mission、Case、Run、Task、Decision、Contract version、Release target、事件与动作标识。记录版本、耗时、尝试、模型/工具、成本、覆盖、权限拒绝、等待、原始错误、outbox 积压、索引水位和 readback 结果；秘密和客户原始行不默认持久化。

产品指标候选包括定义完成周期、人工协调/中断、等待时间、返工、证据完整度、下游一致性、每契约成本及不可复用 FDE 工时。自主推进率与补证质量必须一起看，不能用更多模型调用或更少人工介入单独证明成功。没有客户基线前不编造目标值。

### 8.4 Web 流程可视化

候选工作台包含目标入口、Mission 详情、受控待办、规范方案及契约视图。创建入口不要求选择旧 Contract；创建场景呈现候选方案、样例/反例与首份规范，修订场景再展示旧/新 diff。Mission 执行图显示真实设计、查证、等待和状态版本；Case Map 显示证据、冲突和裁决，两者引用同一批领域标识。

React Flow 仅是候选显示组件。首版支持平移、缩放、筛选与详情定位，不允许拖线改变执行逻辑；审批在受控任务表单中完成。重连、过期、部分、错误、未知与权限状态必须可见，不能用预设动画伪装 Agent。

图不能成为唯一入口：提供等价列表/时间线、键盘访问、明确焦点与文字状态；颜色不独立承担含义。保留可关闭动效、窄屏阅读、缩放与屏幕阅读器路径。Archify 只是静态设计文档，不是 React Flow 或产品运行验收。

## 10. 实施顺序、迁移与回滚

本节解释已获批准路线的依赖关系：电商高潜客户识别为创建主场景，首轮保留修订保护测试。§10.1 只细化既有 Phase 0 的验证基线，不新增开发阶段、不修改路径图；任何路径不能因规格写入而宣称完成。

分阶段验收以 PRD §15.4/§18 为准：Phase 0–1 的 fake 回放只报告工程控制；Phase 2 独立验证真实设计与对应 Web 人验，两者和工程控制均通过后才报告创建主场景 FUNCTIONAL PASS。完整修订闭环后置，首轮保护测试不等于 REVISION PASS；沙箱效果和客户结果另验。PRD §5.5 的状态归属、草案/批准身份、双时间、回应恢复、权限及独立消费检查须在对应实施门细化，不借本次文档修订冻结 schema、关系基数或策略。

| 路线图路径 | 承接内容 | 下一步门与回滚边界 |
|---|---|---|
| 一：产品与架构 | 对齐目标、候选架构、完整失败/验收讨论；独立批准 DBOS 有界验证 | 报告与关键试验通过后才冻结必要选择；Mission 图静态与人类视觉交互验收通过，系统图人验、逐项视口记录和技术验证未齐 |
| 二：Mission/上下文/持久状态 | 创建与修订的最小领域契约、事务/审计/outbox、权限与索引 | schema/接口逐项确认，创建不强制旧版；可导出/恢复，不依赖供应商私有状态 |
| 三：自主推进/中断恢复 | 规范结构/方案设计、受控动作、补证、唤醒与影响；创建做方案对比，修订做旧/新差异 | fake Pi 流验证失败与恢复；真实模型/资料另批；可暂停 Agent 并保留 Case |
| 四：全栈 Web/demo | 实际事件投影、图/列表、任务和契约视图、七分钟闭环 | 自动检查后人类 Browser 验收；fixture 与真实效果分开 |
| 五：沙箱发布/观察 | 一个目标 compile/diff/validate/authorize/publish/verify/rollback/observe | 逐目标授权、读回和回滚演练；未知结果暂停扩散 |
| 六：真实小团队试点 | 基线、成本、协调负担、第二案例复用与获授权下游 | 不能用演示证明客户收益；无证据则缩小或停止假设 |
| 七：仓库/Pi/生产化 | 精确 inventory、独立 Pi fork 与 app 包依赖目标、供应链/运维 | 迁移、远端、发布和生产分别批准；本轮无任何拓扑改变 |

迁移与退出应遵循以下边界：

1. 保留既有 semantic-agent/semantic-web 能力作为复用输入，逐接缝核对；本轮不删除旧代码，也不宣称自动兼容。
2. 每次 schema 或业务规则变化都明确历史读取与迁移方式；是否保留兼容窗口由人类决定，不默认永久兼容。
3. 更换持久引擎时先暂停新领取、列出在途/等待/未知副作用，核对领域版本与收据，再决定排空、迁移或重建；不能直接把旧 history 喂给新引擎。
4. 索引采用可对账的重建与切换候选；重建失败不能覆盖现有可用数据，撤权与删除必须先被尊重。具体并行/切换机制待实现门。
5. 下游发布先只读/影子/提案，再单目标沙箱；源/目标版本、diff、授权、preflight、回滚动作与读回查询绑定同一发布记录。
6. 回滚不是删记录。保留原 Decision、发布结果、补偿、失败收据与影响范围；不可逆效果必须提前显式拒绝或另行接受风险。

### 10.1 高潜客户规范验证包：Phase 0 静态材料与待执行验收

#### 10.1.1 目标、事实与本轮交付

沿用 PRD §5.1 的模拟任务：帮助团队确定哪些已有购买记录的客户值得优先维护，并从零建立可复用的指标、数据与业务规范。业务目标、讨论意见与角色均为模拟输入，不代表 Olist 或真实公司的需求、政策或委托。

业务成功对象是有依据、可复验并经有权人裁决的 Contract v1，而不是固定名单或固定 RFM 公式。当前运营规则与未来购买预测分开：缺少未来标签不自动阻塞前者；净收入、利润、信用、未来价值和增量效果没有证据就不宣称。可执行表示受控检查或消费者能解释规则与映射，不授权任意代码或下游写入。

本节把验证包拆成可检查的四类材料：自有事实及字段说明、模拟目标与约束、角色与授权依据、独立评估断言。本轮已生成相应静态文件，未运行产品 Agent 或交付真实 Contract；素材完成、工程控制、真实设计、产品人验和客户结果仍按 PRD §15.4 分开。

本轮使用可手工复核的小型自有枚举与已确认 JSON/Markdown 形式，不复用 Olist 原始行、评价或派生名单。保留五组事实而非直接提供已分好的客户宽表，是为了检验关联与粒度，代价是需要显式映射。包内物理格式不是产品公共 Schema；大规模随机数据留待有性能问题时讨论，Olist 的真实数据检查仍独立授权。

本轮 [manifest](./validation/high-potential-customer-v0.1/manifest.json)、[context](./validation/high-potential-customer-v0.1/input/context.md) 与[质量报告](./validation/high-potential-customer-v0.1/evaluation/quality-report.md) 记录实际文件哈希、来源/许可标签、枚举方法、行数/键、字段/单位/缺失含义、覆盖与时点，以及模拟角色/策略版本和声明的允许路径。没有随机生成器或随机种子。离线 profile 已核对主键、孤儿、时间、币种、空值、粒度和联结计数并保留分子/分母；这不是产品读取、权限执行、状态机或业务效果测试。

#### 10.1.3 输入与评估隔离

#### 10.1.4 模拟目标、角色与补证主线

目标卡需明确：已有购买记录的客户、当前运营维护用途、可用事实范围、成功条件及尚待裁决的资源约束。不给固定阈值、权重或唯一识别公式；候选规则由 Agent 依据事实提出，关键裁量按 PRD FR-05 比较可行方案。没有适用旧 Contract 的创建依据须来自有权且覆盖明确的模拟资料，而不是搜索无结果。

| 模拟主体 | 本场景职责候选 | 权限边界与反例 |
|---|---|---|
| 发起人 | 提交/澄清目标、查看获权进展、提出取消 | 发起不自动获得业务批准权；不能代替数据负责人证明字段事实 |
| 事实提供者 | 确认客户关联、收款含义、覆盖与缺失，提交有来源的补证 | 不替业务负责人选择运营规则；不知道的退款/成本事实不能补造 |
| 业务裁决者 | 选择目标与资源约束、裁决候选和适用例外、批准明确版本 | 批准限本范围、版本和策略；不能把错误计算、未知事实或越权变为合法 |

本轮 context 已将这份矩阵落为中性合成主体和明确范围/版本/时点的资料；它不是已部署 IAM 或已冻结 RBAC/ABAC 策略，也不能自授权限。产品实施前仍需确认真实认证主体、能力、角色冲突、委托、有效期与撤权接缝。单人演示可显式切换三个主体，但要记作单人角色扮演；不得记为真实 2–5 人协作。没有可验证责任依据时保留阻塞，不能因为角色名存在就发任务。

历史分析 T0/T1 只约束历史事实视图，不提供当前动作授权。每次读取、发任务、接收补证或审批时，都需按动作发生时的当前 actor、role、resource、action、scope、Case、适用的候选/Contract 版本与 target、policy 重新做服务端校验；撤权、委托撤回、策略过期或范围变更不能沿用 T0 的授权。以上是校验维度，不冻结字段名，也不要求合法创建预先具备 Contract 或 Release target。

主线候选准备一处与候选方案相关的资料缺口，例如“退款覆盖尚未确认”。Agent 应先判断现有证据是否已足够，选择受控查证或最小补证任务，不为展示强制发问；事实提供者可以如实确认“当前没有退款来源”，业务裁决者再选择与现有事实相容的运营规则。未提供退款不等于零退款，也不必阻塞不依赖净收入的合法方案。有效回应需绑定任务、依赖版本和主体，经复核后自动恢复；业务裁决不能被 fake 脚本的自动同意冒充真人选择。补证与恢复还须由实际触发关键缺口的独立用例证明；本次运行未触发时不能记该项已通过。
