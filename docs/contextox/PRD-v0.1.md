## 1. 摘要

ContextOx 是从组织目标和全局影响出发，设计、建立并持续演进业务规范的执行 Agent。MVP 验证：

> 即使没有现成适用规范，Agent 能否在授权范围内理解目标、设计规范结构与候选规则、自主查证、发现冲突、寻找责任依据、发起并追踪补证、等待与恢复、准备业务裁决，最终交付可执行、可追溯、可复用的首份规范契约。

人提供目标、必要事实和授权，保留业务裁决、例外接受与高风险发布权，不负责逐步点击推动工作。从零不是没有事实、边界或责任，也不是把模型候选当成组织既定政策。

首轮以“哪些已有购买记录的客户值得优先维护”为模拟任务，使用自有电商测试数据，交付高潜客户识别规范的 Contract v1、字段映射、规则检查、样例/反例、证据与裁决记录、只读影响说明和发布提案。“高潜”是待裁决的运营优先级定义，不是已经验证的未来购买概率；客户分组只是规则的只读验证结果，不是产品交付终点。

工程回放、真实模型设计能力、人类产品验收和真实客户价值分开验证。首轮不要求旧 Contract 或外部发布；后续经单独授权验证一个沙箱目标，再进入真实团队试点。契约已批准、已导出、下游已生效与发布已读回是不同状态。

## 2. 已知事实、假设与待验证边界

### 2.1 已知事实

- 当前仓库已有 `packages/semantic-agent`，包含 source discovery/binding、ContextPack、AnalysisPlan/QueryPlan、preflight、evidence/trace、受控工具、RuntimeHost 和 Pi adapter 等确定性内核原语。
- 当前这些能力主要是内存、fixture 和契约验证；没有真实数据库执行、企业身份、持久工作流、通知协作、Definition Change Case、Business Definition Contract、下游发布或 Web 产品闭环。
- Path 05 架构报告中的 local-first 单用户 Web 方向是历史设计输入；其 5.1–5.7 未实现，Browser 验收为 `NOT RUN`，不能视为新 ContextOx 企业产品的既定架构。
- 公开竞品已经覆盖目录、业务上下文、AI 建议、审批、影响、规则执行或持续治理中的多项能力。ContextOx 的差异尚未通过市场验证。
- 2026-08-31 的仓库核对仅找到零散订单/客户 Schema、预设指标 Binding 和结果 fixture；旧数据计划仍为 PROPOSED，没有核验到完整外部订单数据或完成导入的证据。这不是全量原始数据质量验收，也不排除仓库外另有资料。
- Olist 与 AdventureWorks 是旧项目候选来源，不是新验证的已接入数据。统一自有验证包尚待实现授权；模拟业务任务、角色或公开数据不能证明真实公司的需求、政策、责任或付费意愿。
- 复用依据见 [旧数据计划](../alphaox/path-06/development-plan.md)、[Schema 样例](../../packages/semantic-agent/test/discovery.test.ts)、[预设指标 Binding](../../packages/semantic-agent/test/binding.test.ts)和 [Context Pack 样例](../../packages/semantic-agent/test/context-pack.test.ts)。

### 2.2 产品假设

- 专业用户自助发起、共 2–5 人参与一个限定业务域，是可行的启动方式；买方、预算与真实 ICP 尚待验证；
- 电商高潜客户识别易于讲清“目标—事实—候选规则—裁决—可复用规范”的关系，适合验证规范创建、证据与协调能力；单个案例不证明跨行业适用性；
- Agent 设计方案并主动推进补证，比固定流程与人工催办更省协调成本且不降低控制；
- 团队愿意维护有版本、责任、验证和生效规则的共享规范，而非只要一次性文档；
- 真实试点愿意提供最少获授权来源及责任主体，并在独立发布门后连接一个可验证目标；
- 历史交易可支持客户特征与运营分层候选，但“值得优先维护”的目标、约束和最终规则需要明确业务裁决；未来价值、意向、信用或增量转化不能从订单字段自动成立。

### 2.3 不得当作事实的内容

- 竞品没有同类私有能力；
- Agent 一定能减少会议或提高转化；
- 所有行业都需要同一种业务定义契约；
- 上线后结果变化由定义变更单独造成；
- 一次试点成功即可证明可规模化销售或通用架构正确；
- 模拟需求、角色扮演、公开数据或合成数据代表真实客户需求与组织政策；
- fake model 的固定输出证明真实 Agent 会设计规范；
- 字段可计算就代表业务含义正确，或旧 Binding 可直接充当从零设计的输入答案。

## 3. 目标、非目标与成功边界

### 3.1 v0.1 目标

1. 验证 Mission 持续推进、Case 保存业务事实与决策、Agent Run 有界执行的分工；公共字段和最终命名仍待架构门；
2. 无旧 Contract 时能合法开始，并由 Agent 提出规范结构、候选规则与取舍；
3. 将指标定义、数据粒度/关联/时间/质量规则、职责/例外/批准/复审规则贯通到首份规范；
4. 以有来源的任务完成补证、异议和裁决，有效回应后自动恢复，不依赖人逐步推动；
5. 形成机器可验证、双时间、可审计的 Contract v1、映射、检查、样例/反例、只读影响说明和发布提案；
6. 首轮验证创建/修订判别、旧版绑定与历史不覆写的保护边界；完整已有规范修订闭环后置，不能伪造 v0 或把检索未命中当成无既有规范；
7. 验证权限拒绝、证据缺失/过期、粒度与关联错误、模型失败、任务重复/过期和批准失效；
8. 记录实际运行、人工协调与测试覆盖；真实客户效率基线和收益在后续试点建立，单目标发布/readback/rollback 在独立沙箱阶段验收。

### 3.2 v0.1 非目标

- 通用自然语言查询、自动生成任意 SQL 或 ChatBI；
- 自建完整数据目录、血缘扫描、指标引擎、主数据、BI 或 IAM；
- 同时支持多个行业、十种定义类型和大量连接器；
- 无人工授权的生产发布或业务裁决；
- 自适应自治 Agent 组织作为卖点；
- 证明业务因果收益；
- 全自动迁移现有 AlphaOx 产品和品牌；
- 在本 PRD 中决定 SaaS、私有化、单体/服务化、数据库或工作流引擎。

## 4. ICP、采购触发与角色

### 4.1 初始入口与真实试点准入

初始入口是一个专业用户发起、共 2–5 人参与的限定业务域，不要求先拥有中大型企业客户。开发验证可使用自有数据和模拟角色；单人扮演多个角色时必须标注，不能记为真实多人协作结果。

真实试点前必须确认：

- 有实际的规范创建或修订任务及成功条件，而非只有几张表；
- 有获授权的最少数据/元数据、必要业务事实与可确认的责任主体；
- 发起、事实提供、业务裁决、安全和发布职责可辨认，角色合并服从职责冲突政策；
- 能记录现行做法、协调成本与测量基线，未知项保留未知；
- 进入外部发布阶段时，另行确认目标 Owner、授权、readback 和回滚能力。

中大型企业、采购与企业集成保留为后续验证方向，不作为自有 fixture 功能演示的先决条件。

### 4.2 采购触发

- 新团队、业务或 Agent 项目需要从零建立可共用、可验证的规范；此触发是否形成独立预算仍待真实证据；
- AI/Agent 项目因口径冲突无法进入生产；
- 数据治理或指标平台已部署，但关键变更仍靠会议和群聊；
- 组织重组、业务模型变化或监管要求导致定义频繁变化；
- 报表、模型和运营动作使用不同版本，造成损失或审计压力；
- 数据平台升级或“数据要素/标准化”项目需要把人的决策变成可执行资产。

### 4.3 角色与权限

| 角色 | 最小职责 | 禁止默认赋予的能力 |
|---|---|---|
| Sponsor | 选定试点、移除组织阻塞、确认成功基线 | 代替所有领域 Owner 批准定义 |
| Case Owner / Data Steward | 维护案例完整性、路由争议、组织决策 | 无授权修改下游生产系统 |
| Business Owner / SME | 对业务语义、范围、例外提供有权判断 | 查看不属于其范围的敏感数据原文 |
| Data/Metric Owner | 确认实现映射、影响、测试和可发布性 | 以技术可实现性替代业务裁决 |
| Security/Compliance | 决定数据用途、访问、保留和例外 | 直接修改业务定义内容 |
| Approver | 对指定范围、版本和有效期批准/拒绝 | 将批准权自动转授给 Agent |
| Publisher/System Owner | 在授权后执行目标级发布与验证 | 修改未经批准的契约内容 |
| Observer/Auditor | 查看获准范围的历史和证据 | 执行变更或访问敏感原始输入 |
| Agent | 设计规范结构与候选方案、自主查证、组织补证、等待恢复和执行获准工具 | 成为业务真相、代替有权人裁决或隐式超级管理员 |

身份、委托、职责冲突和权限模型必须进入架构讨论，不能只写在 prompt 中。

## 5. 首个场景：从零建立电商高潜客户识别规范

### 5.1 模拟业务任务

> 我们有客户和订单相关数据，但还没有统一的高潜客户识别规则。请帮我们确定哪些已有购买记录的客户值得优先维护，并建立一套团队、报表和其他 Agent 都能复用的规范，说明判断依据、适用范围，以及资料不足时怎么办。

这是能力验证的模拟任务，不代表 Olist、AdventureWorks 或任何真实公司的委托。当前示例对象是已有购买记录的电商客户，不默认扩成陌生销售线索、企业信用或未来终身价值预测。没有旧 Contract 可以开始；仍需核对业务事实、上位约束、角色与授权。

主场景仍贯通指标、数据规范和业务规范。“高潜”可以由 Agent 提出多个有依据的候选解释，再由有权人选择适用目标和规则；不能把一次高消费、历史高价值或模型分数直接说成已验证的未来潜力。具体阈值、权重、窗口和纳入/排除由案例证据与裁决产生，不预设唯一 RFM 公式或给模型现成答案。

缺少未来购买标签不自动阻塞当前运营优先级规范：在已确认的当前运营目标下，只要观察窗内事实、约束、权限和业务裁决足够，就可创建首版；未来购买概率与效果结论仍为未验证、不得宣称。若目标改为未来预测，应另行确认任务并建立相应 Case、证据、评估与授权边界，不能以运营分层冒充预测。

### 5.2 最小验证输入与 Olist 边界

- 自有确定性小数据覆盖客户、订单、订单行、支付及必要的履约事实；客户实体与订单级关联键分开，精确 Schema、行数、种子与生成方式在验证实施门确认；
- 3–4 类资料：样例表与结构、字段说明、模拟业务目标与约束、角色与授权依据；不等于连接 3–4 个外部系统；
- 固定数据版本、覆盖窗口、评估时点、时区与币种约定；数据快照、读取/可获得时间和契约有效时间分开；历史样本不以今天为“最近购买”的默认评估日；
- 明确发起人、事实提供者和裁决者；业务目的和约束如实标为模拟输入，不能伪造真实公司的政策或责任目录；
- 不提供最终客户分类、指标定义、已批准完整 Binding 或验收答案；已知事实、必要字段解释和上位约束仍应提供。

此前候选确为 Kaggle 的 [Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/olistbr/brazilian-ecommerce/home)。其公开说明包含客户、订单、商品行、支付、履约与评价等信息；同一客户在不同订单上的 `customer_id` 可以不同，`customer_unique_id` 用于跨订单识别。它适合作为本场景的结构参考与获授权后的真实数据验证候选，不能把订单级键直接当独立客户，也不因此视为已接入。

[原始数据集页面](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)标注 CC BY-NC-SA 4.0；[许可证摘要](https://creativecommons.org/licenses/by-nc-sa/4.0/)包含非商业、署名和相同方式共享条件。具体版本、用途、下载、导入、模型输入与对外演示仍须核验并单独授权，不以第三方重传的宽松标签替代原始来源许可。

本轮只核对来源说明，未下载原始行，未做全量质量、复购密度或时间可用性检查，未证明未来预测能力。工程 CI 与可分发演示继续使用独立编写的自有小样本，不复制 Olist 原始行、评价或派生名单。真实 Olist 数据验证与自有 fixture 各自标记；来源门未通过不阻塞自有工程测试。AdventureWorks 保留为其他来源候选；统一验证包仍待实现。

### 5.3 Agent 必须准备的三层成果

| 层次 | 候选内容 | 验收边界 |
|---|---|---|
| 指标与识别规则 | 近期购买、订单频次、观察窗内消费、可用履约/体验事实，以及候选客户分层 | 明确目的、观察窗、计算口径、纳入/排除和信息不足类别；这些是可选设计方向，不是固定输入公式；历史特征不冒充未来预测 |
| 数据规范 | 客户粒度、订单关联、聚合顺序、时间可用性、币种、重复与缺失处理 | 先对齐客户和订单粒度，再校验多商品/多支付关联；检查能从来源事实复算，不依赖字段名称猜测 |
| 业务规范 | 谁适用、为何优先维护、职责、容量/约束、例外、批准、生效与复审 | 运营选择有依据且由有权人裁决；不发营销消息、不修改 CRM，不把模拟政策说成客户既定规则 |

演示依次呈现：模糊目标 → Agent 查证客户粒度与可用事实 → 提出有取舍的候选 → 对关键缺口派发补证任务 → 回应后自动更新方案 → 人类裁决 → Contract v1 与只读样例。样例需解释被纳入、被排除、信息不足及候选之间发生变化的客户，而非只展示一个漂亮名单。

最终交付首份 Contract v1、字段映射、可执行检查、样例/反例、证据和裁决记录、只读影响说明与发布提案。可执行不是任意代码生成，也不等于已经写入下游系统。

### 5.4 验证包与反例

- 分开保存 Agent 可见输入和评估端断言；测试期望不能经旧 Binding、模板或检索上下文泄漏成答案。记录实际模型可见输入的版本与哈希；
- 验证包清单至少记录来源/许可标记、自有生成方式、Schema 与数据版本、粒度/键、固定时点、可获得时间、角色/策略版本及允许进入模型的字段；当前这些是待实现材料，不是已有数据资产；
- 评估端独立记录必须满足的业务不变量、可接受候选变体、必须拒绝或标为未知的结论，以及反例的预期状态和禁止动作；不以单一公式、固定名单或文案相似度判正确；
- 同一客户跨订单使用不同关联键、一笔订单含多个商品和多笔支付，均需有反例；复购样本不足或只观察一次购买时，不得把未知潜力标为已知低潜；
- 没有退款、成本、意向或营销响应等依据时，应补证、限定目标或阻塞相关结论，不编造净收入、利润、信用、未来价值或增量转化；
- 使用未见样例、同一事实的不同物理 Schema、目标或约束变化验证方案适应；真实模型评估另获授权与预算，fake 回放只证明控制过程；
- 用独立检查器或最小消费者复读契约与映射，在允许的样本上复算，检验可复用性；不以“导出了 YAML”作为唯一通过条件。

### 5.5 首轮验收设计清单：实施前补齐，当前未运行

下表把审查意见收敛成最低反证要求，不冻结数据库、公共字段、关系基数、时间区间或策略实现。进入相应实施门前，主 Agent 与人类需确认每行的精确输入、预期结果、责任人与验证方式；未具备时只阻塞对应实施/验收，不冒充已通过测试。

| 检查 | 最小反例或问题 | 必须保留的结果/禁止动作 |
|---|---|---|
| 客户与聚合粒度 | 同一客户多订单；订单多商品且多支付 | 人数/金额不被关联放大；无法确认跨单身份时补证或限定判断 |
| 语义与时间可用性 | 单次大额、稀疏复购、缺退款；评估时点之后才获得的评价/履约信息 | 规则与目标相符，未知如实标注；不偷看未来信息，不把历史消费或可计算金额冒充潜力/利润 |
| 无未来标签的正向创建 | 有当前交易事实与已确认运营目标，但没有未来购买标签 | 当前条件满足后可创建运营优先级规范；未来预测保持 UNKNOWN/未验证，不要求先造标签或预设名单 |
| 创建与版本保护 | 无旧版合法创建；修订缺基线；候选或批准依赖变化 | 创建不造 v0；修订不得绕过基线；冻结草案、Decision 与批准版本的身份可追溯，失效批准不得用于新动作 |
| 证据缺口与例外 | 普通“继续”、笼统接受缺口、例外过期或超范围 | 按 §6.2/§11 的不可绕过要求检查；记录例外依据，不由点击动作创造未知事实或权限 |
| 人类回应与恢复 | 过期/旧版本、重复/乱序、委托撤回、取消或关闭后回应 | 区分拒绝、去重、合法保留证据与有效唤醒；旧回应不能满足新任务，通知失败不抹去已建任务 |
| 双时间 | 迟到证据、历史更正、未来生效、有效期边界与范围重叠 | 给出明确 as-of 查询及预期可见结果；历史不能因回填被无痕改写，区间/时区政策先确认 |
| 权限与角色 | 无权对象恰好与新 Case 相似；角色冲突；任务解释泄密 | 权限策略先确认；不泄漏隐藏对象的存在性，也不把“脱敏冲突”默认当安全方案 |
| fixture 复审 | 已交付契约、无外部发布时收到模拟信号 | 在授权范围提出/创建新关联 Case，保留审计；不伪造 PUBLISHED/OBSERVING 或改旧批准 |
| 独立消费 | 契约导出后由另一受控消费者读入 | 规则、映射、版本、证据及限制可追踪并复验；工程/真实模型/人类验收分别记账 |

### 5.6 真实试点基线与后续案例

真实试点前记录定义完成周期、参与角色与人次、会议/消息/工单交接、返工原因、现行规则和实现位置、历史遗漏与错误动作、发布/验证步骤，以及观察指标的窗口和混杂因素。没有历史定义或测量时如实记录缺口，不制造 v0、现状数值或效率提升。

完整已有规范修订、扩展销售线索/信用或其他领域保留为后续案例，分别补齐事实、授权和需求证据。首个电商客户规则案例通过，不代表未来预测准确、跨行业通用、真实客户价值或商业可行性通过。

## 6. Mission 与 Case 的创建/修订生命周期

Mission 负责持续推进和唤醒，Case 保存规范方案、事实与决策，Agent Run 是有界执行。下表讨论 Case 的候选业务生命周期；Task、Run、Evidence、Decision 与目标级 Release 有各自状态，§14 的可见结果不是同一枚举。它不是必须由人逐步点击的流程，也不冻结公共字段或对象基数。

### 6.1 状态

| 状态 | 进入条件 | 允许动作 | 退出条件 |
|---|---|---|---|
| `INTAKE` | 有目标、提出人和初始范围 | 确认创建/修订条件与 Owner；修订绑定旧版，创建不强制旧版 | 最小输入与授权通过校验 |
| `DIAGNOSING` | 案例已被接受 | 查证现状与约束，设计规范结构和初始候选，发现证据/责任依据及缺口 | 初始方案与案例图可审阅或显式 `BLOCKED` |
| `COLLECTING` | 已生成待补信息 | 派发、完成、拒绝、委托、升级微任务 | 关键证据齐备；仅可按 §6.2 接受获授权且不触及硬约束的明确例外 |
| `DELIBERATING` | 至少一个定义候选 | 比较候选、提出反例/异议、记录保留意见 | 形成可批准候选或明确无法达成 |
| `SIMULATING` | 候选语义与映射足以测试 | 运行只读/fixture 校验；创建比较候选与可观察现状，修订比较绑定旧版 | 满足当前阶段验证要求；缺口明确 |
| `APPROVAL_PENDING` | 候选契约与影响包冻结 | 批准、拒绝、要求修改、委托（如政策允许） | 所需批准完整且无阻塞变化 |
| `APPROVED` | 指定版本、范围、有效期已批准 | 交付契约、验证说明与发布提案 | 成功条件满足则关闭；外部发布另需目标级授权与预检 |
| `PUBLISHING` | 某目标已获单独授权 | 预览、执行、验证、重试或目标级回滚 | 所有目标终止于成功/失败/已回滚/取消 |
| `OBSERVING` | 至少一个目标成功且契约生效 | 采集采用、异常和结果信号；提出复审 | 到达观察门或出现紧急回滚条件 |
| `CLOSED` | 结果与遗留风险已记录 | 只读审计；允许发起新 Case | 新变化必须创建关联 Case，不覆写历史 |
| `BLOCKED` | 权限、证据、责任人、策略或外部系统阻塞 | 补齐条件、取消或保留阻塞 | 原因被解决并返回合法前态 |
| `CANCELLED` | 有权人取消且无未处理发布 | 只读审计 | 终态；后续需求创建新 Case |

### 6.2 状态规则

- 状态转换必须由显式 command 触发并产生领域事件；
- Agent 只能执行策略允许的转换，不能通过改文本绕过状态；
- 任何关键证据、候选、映射或批准后发生变化，都必须使相关审批失效或要求重确认；
- `BLOCKED`、部分发布和回滚必须是一等状态，不得包装成 `SUCCESS`；
- 一个 Case 可以有多个 Release target，但每个目标有独立状态和回滚边界；
- 旧契约版本不可原地覆写；更改创建新版本和关联 Case。
- 无适用旧规范的合法创建可形成首份 v1；修订必须绑定旧版，不能用创建模式绕过版本检查。
- 未找到、无权读取和已确认不存在是不同情况；关键事实、权限与计算正确性不能由普通“继续”或笼统接受缺口替代。
- 可接受例外必须有适用策略与有权主体，记录缺口、依据、范围、风险、有效期、允许动作和补证责任，并绑定当前候选及依赖版本；无明确策略时保持阻塞。例外不能创造事实、纠正错误计算或越过权限；缩小目标需重新校验受影响方案和批准。
- 首轮可在契约与提案交付后按成功条件结束；不强制发布、观察或无限循环。已批准、已导出和下游已生效分别记录。

### 6.3 典型流程

业务目标建立 Mission → 核对创建/修订条件、权限与上下文 → Agent 设计规范结构和候选方案 → 受控查证与补证 → 有效回应自动恢复并更新方案 → 样例、反例与只读影响校验 → 有权人裁决 → Contract v1 与发布提案 → 按成功条件结束。

已有规范修订使用绑定旧版与旧/新比较，形成后续版本。授权观察信号可提出复审；fixture 信号不能当成真实采用。沙箱目标的预览、授权、发布、readback、回滚和观察是后续独立阶段，不是首轮闭环必经步骤。

## 7. Agent 生成的 Proposal Map

Proposal Map 是可审阅的候选关系图，不是事实图谱。至少包含：

- **Goal**：为什么创建或修订规范、适用范围、约束、截止与成功信号；
- **Existing Context**：可见的现行实践、上位约束与覆盖缺口；已确认存在适用旧定义时记录版本、范围、时间和使用方，创建不强制提供旧 Contract；
- **Evidence Nodes**：来源、时间、权限、摘要、支持/反对关系；
- **People/Role Nodes**：候选责任、授权依据、可替代/委托关系；
- **Candidate Standards**：规范结构、指标与数据规则、职责、包含/排除、阈值、例外、验证方法及方案取舍；
- **Disputes**：争议点、提出者、反例、状态和裁决；
- **Impact Nodes**：系统、指标、报表、模型、Agent、流程和人群；
- **Microtasks**：缺口、接收人、依赖、截止和完成标准；
- **Uncertainty**：未知、陈旧、冲突、推断和未获权限；
- **Release Targets**：目标版本、预览、策略、验证和回滚能力；
- **Outcome Signals**：观察方法、时间窗、基线和混杂因素。

每个 Agent 生成节点必须有 `generated_by`、输入引用、模型/工具版本、生成时间、置信/不确定性和人工状态。人工确认不应删除其机器来源；机器更新也不能覆写人的签名决定。

## 8. Human Microtask

### 8.1 最小字段

- 稳定 ID、Case ID、类型和版本；
- 为什么需要此人、其授权或专业依据；
- 只与任务相关的最小上下文；
- 明确问题、可选动作和完成标准；
- 所依赖证据、候选或前置任务版本；
- 截止、提醒、升级和委托规则；
- 敏感等级、访问范围和链接有效期；
- `completed / rejected / delegated / expired / cancelled / blocked` 状态；
- 完成人、时间、输入摘要、保留意见和后续影响。

### 8.2 任务类型

- 补充证据；
- 确认业务事实、约束、Owner 和使用方；仅在适用时确认现行定义；
- 解释例外或边界；
- 对候选提出异议或反例；
- 确认技术映射；
- 确认影响和迁移；
- 安全/合规审核；
- 业务批准；
- 发布授权与发布后验证；
- 结果解释与复审建议。

### 8.3 交互原则

- 接收者不需要先阅读完整 Case；
- 系统必须说明“为什么找你”和“不处理会阻塞什么”；
- 有效任务回应形成领域事件并唤醒 Mission，重新校验权限、版本与新鲜度，而不是要求人手工找下一个人或点击继续；
- Agent 可以建议提醒/升级，但所有规则可见且服从组织政策；
- 对模糊回答追问时必须保留原回答，不得静默改写；
- 过期任务提交必须重新验证其依赖版本；重复、乱序、委托撤回、已取消/关闭后的回应还须分别定义持久化、拒绝/去重与唤醒行为，见 §5.5。仅保存回应或通知已送达不等于任务有效完成。

## 9. Business Definition Contract

### 9.1 目的

契约是被批准定义的机器可验证表示，是多个下游表示的上层控制对象。它不取代所有指标、目录或数据契约格式。

### 9.2 v0.1 最小结构

```yaml
contract_id: stable-id
definition_type: business_standard
name: 电商高潜客户识别与运营优先级规范
version: 1
status: draft
scope:
  organization: fixture-org
  region: example-region
  product: example-product
semantics:
  statement: candidate-definition-pending-approval
  inclusion: []
  exclusion: []
  examples: []
  counterexamples: []
  rules: []
responsibility:
  owner_ref: role-or-user-ref
  reviewers: []
  approvers: []
time:
  recorded_at: timestamp
  effective_from: timestamp
  effective_to: null
evidence_refs: []
policy_refs: []
mapping_refs: []
exception_refs: []
validation_refs: []
decision_refs: []
change_case_ref: case-id
supersedes: null
release_policy_ref: policy-id
observation_plan_ref: plan-id
```

这是未批准草案的概念示例，不是已批准 Schema 或可通过验收的完整契约；version: 1 表示首版目标，不代表批准或生效。business_standard、rules、validation_refs、decision_refs 和空旧版引用均为候选表达，字段类型、签名、基数与互操作格式仍须架构门。实际批准前必须具备适用的规则、映射、检查、例外、责任、证据与裁决引用；创建不要求旧版，修订必须绑定明确旧版。草案身份、待批准冻结指纹、Decision 与不可变批准版本的对应关系，以及哪些依赖变化使批准失效，需按 §5.5 在领域实施门确认；不得从示例的 draft/v1 推断可原地改写批准历史。

### 9.3 双时间要求

- 记录时间和业务有效时间必须分离；
- 支持未来生效、历史回填、定时失效和并行范围；
- 同一范围和定义类型发生有效期重叠时必须检测并阻塞或进入显式例外；
- 更正历史记录不能删除原审计事实；
- 所有查询和下游发布必须显式选择 `as_of_recorded` 与 `as_of_effective` 或采用已批准默认策略。

## 10. 下游编译、发布和回滚

### 10.1 后续单目标沙箱接缝

首轮只交付发布提案，不写入外部目标。另获沙箱实施和目标级授权后，只接一个可回滚目标，并区分：

1. `compile`：从批准契约生成目标候选，不产生外部变化；
2. `diff`：与目标当前状态对比；
3. `validate`：检查格式、策略、兼容和权限；
4. `authorize`：有权人对目标、版本、窗口和影响单独批准；
5. `publish`：幂等执行；
6. `verify`：从目标读回实际状态；
7. `rollback`：恢复预先记录的安全点；
8. `observe`：记录使用和异常，不更改契约。

### 10.2 发布规则

- Chat 中的“同意”不能被模型自行解释为生产授权；
- 授权必须绑定 Case、Contract version、target、diff、actor 和过期时间；
- publish 返回成功不等于业务完成，必须 readback 验证；
- 多目标不能用一个布尔值概括；必须逐目标报告；
- 部分失败保持 `PARTIAL`，明确哪些目标成功、失败或回滚；
- 不支持回滚的目标在接入前必须显式风险接受；
- 适配器不得把第三方错误改写成模糊“发布失败”。

## 11. 功能需求

### FR-01 Mission / Case Intake

- 从人工请求或受控 API 建立 Mission 与关联 Case；最终关联基数待契约门；
- 要求目标、范围、提出人、成功条件、授权边界与截止/触发原因；创建不强制旧定义，修订要求明确旧版；不确定现状时保留查证状态；
- 检测可能重复或冲突的开放 Case；
- 缺少 Owner 或范围时进入 `BLOCKED`，不虚构默认。

### FR-02 Evidence Discovery

- 首轮从自有 fixture 的 3–4 类资料发现业务事实、约束、责任依据、映射和使用证据；后续真实或外部来源按最少范围另行授权；
- 每条证据保留来源、读取时间、业务时间、权限和新鲜度；
- 区分自有测试事实、模拟需求/角色、真实来源事实、人工陈述、Agent 候选/推断和不可访问项；来源事实不自动授予批准权；
- 原始敏感数据默认不复制到案例或模型上下文，仅保留最小摘要/引用。

### FR-03 Proposal Map

- 生成候选关系并说明来源和不确定性；
- 支持人工确认、纠正、拒绝或标记未知；
- 新证据到达时生成差异，不静默覆写已审阅节点；
- 图形视图不是唯一可访问方式，必须有列表/文本等价表达。

### FR-04 Human Task Orchestration

- 根据缺口提出最小任务、接收角色和依赖；
- 支持接受、拒绝、委托、补充、过期、提醒和升级；
- 记录任务版本，防止对过期上下文提交；
- 任务渠道失败、用户离职或无权限时进入显式阻塞。

### FR-05 Candidate and Dispute

- Agent 主动设计规范结构、规则、职责与验证方式；对有裁量的关键规则比较至少两个候选并说明取舍，只有单一合法方案时说明约束与被排除方案；
- 记录异议、反例、保留意见和解决理由；
- Agent 可以总结，不能替裁决者关闭争议；
- 关键争议未解决时禁止进入批准；可接受例外必须满足 §6.2 的范围、策略与审计要求，不能绕过关键事实、计算正确性或权限。

### FR-06 Impact Simulation

- 显示受影响的系统/指标/流程/人群和证据来源；
- 用受控只读能力或 fixture 校验规则和映射；创建比较候选方案与可观察现状，修订比较绑定旧版，不伪造 v0 或历史效果；
- 标注数据覆盖、新鲜度、样本/全量、失败和不可计算项；
- 不把订单金额、支付金额等可计算字段自动解释为已成立的净收入、利润或客户潜力；业务含义与缺失资料分别说明；
- 模拟不得自动触发外部写入。

### FR-07 Contract and Approval

- 生成含规则、责任、映射、检查、样例/反例与证据的 Contract 草案和人类可读说明；合法创建批准后形成首份 v1，修订形成后续版本；
- 冻结待批准版本；任何实质变化使相关批准失效；
- 支持按范围/角色的审批、拒绝、要求修改和保留意见；
- 完成时记录实际授权主体和策略版本。

### FR-08 Release Control

- 首轮仅准备发布提案，不实现外部写入；后续沙箱阶段实现 compile/diff/validate/authorize/publish/verify/rollback 接缝；
- 后续先接一个目标，单独取得实施与目标授权，并在沙箱完成 readback 和回滚演练；
- 所有外部动作幂等、可追踪并保留原始错误；
- readback 与期望不符时状态为失败或部分，不能声称完成。

### FR-09 Observation and Reopen

- 记录采用、异常、人工反馈和业务结果信号；首轮只用明确标注的 fixture 信号验证复审控制，不将其计为真实采用或业务结果；
- 标明测量来源、窗口、口径和混杂因素；
- 首轮已交付/关闭的 Case 可在授权范围收到 fixture 信号并提出或创建新关联 Case，记录信号、理由、授权与新旧关联；不要求先进入仅供真实目标生效后使用的 OBSERVING，不伪造 Release 成功，也不自动续用旧批准；
- 紧急回滚仍需预定义授权，执行后保留原因和后续任务。

### FR-10 Search and Audit

- 按定义、版本、Case、Owner、系统和时间检索；
- 审计者能重建某版本为什么成立、谁批准、发布到哪里和实际读回什么；
- 权限不足时搜索结果不得泄漏标题、摘要或存在性；
- 审计导出必须可验证完整性并受保留/访问策略控制。

## 12. 安全、隐私与合规需求

### SEC-01 身份与会话

- 首轮具备明确标注的 fixture 主体与权限；真实来源或多人试点前接入适用的可信身份，企业标准协议按实际需要确认；主体 ID 与显示信息分离，演示身份不能用于真实访问；
- 禁止共享 Agent 超级账号；
- 会话过期、撤权、离职和委托必须及时反映；
- 高风险动作要求重新认证或等价强确认的可行性进入架构评审。

### SEC-02 授权

- 所有读、建议、任务、审批和发布动作做服务端授权；
- 授权至少考虑 actor、role、resource、action、scope、case state、contract version、target 和 policy version；
- UI 隐藏按钮不构成授权；
- 默认拒绝，未知策略/身份状态 fail closed。

### SEC-03 数据最小化

- 证据优先引用和摘要，不复制原始数据；
- 模型上下文只包含完成当前步骤所需字段；
- 日志、trace、通知和错误中不得出现未脱敏敏感原文；
- 外部模型、遥测和跨境路径必须可配置并在试点前书面确认。

### SEC-04 工具与发布

- 工具白名单、输入 Schema、权限和风险级别由代码/策略强制；
- 模型不能生成或扩大 capability；
- 写工具默认禁用，按目标和版本临时授权；
- secret 不进入 prompt、代码库、普通日志或审计导出。

### SEC-05 供应链

- 新依赖精确锁版、审查 license/release notes/install scripts/依赖树；
- 连接器和模型 provider 版本进入 trace；
- 上游升级必须跑兼容契约和 fail-closed 反例；
- 私有化客户所需补丁和漏洞响应 Owner 必须明确。

## 13. 审计与可观测需求

### AUD-01 领域审计

必须以不可变或防篡改策略记录：

- Mission 与 Case 状态变化；
- Evidence、Candidate、Dispute、Task 和 Contract 的版本变化；
- 身份、授权和策略决策；
- 审批、拒绝、覆盖、委托和例外；
- 发布预览、授权、请求、响应、readback 和回滚；
- Agent 使用的模型/工具版本、输入引用和输出摘要。

### OBS-01 系统观测

- 统一 correlation ID 串联 request、Mission、Case、Agent Run、Task、Decision、Contract 和适用的 release target；
- 指标至少覆盖延迟、错误、重试、任务等待、阻塞、token/成本、发布结果和 adapter 健康；
- trace 与领域审计分离，trace 丢失不能导致审计丢失；
- 部分失败和陈旧证据有独立指标与告警；
- 模型质量 eval 使用去标识化测试集，不用生产真相做隐式训练。

### OBS-02 产品测量

- 每个产品指标带定义、Owner、来源、时间窗口和版本；
- 指标口径本身发生变化时也要走受控变更或至少显式版本化；
- dashboard 只展示实际读取状态，不用历史任务成功或终端退出码代替当前健康。

## 14. 失败与状态矩阵

| 失败 | 系统行为 | 人类可见状态 | 恢复边界 |
|---|---|---|---|
| 已确认合法创建且无旧 Contract | 在目标、范围、事实与授权足够时设计首份规范；不伪造 v0 | 可创建首版 | 不因缺少旧版本阻塞 |
| 未找到、无权读取或尚未确认适用规范 | 区分覆盖不足与不存在，受限查证或补证 | `PARTIAL / BLOCKED` | 澄清现状；不得自动切成创建 |
| 修订未绑定可验证旧版 | 停止修订与旧/新比较 | `BLOCKED: baseline_missing` | 指定正确基线，不以创建绕过 |
| 关联放大、关键字段缺失或语义依据不足 | 暂停相关计算与批准，给出反例、影响范围与补证问题 | `PARTIAL / BLOCKED` | 修正映射、补证或明确缩小目标；不能捏造数值与政策 |
| 来源过期或只返回部分数据 | 保留覆盖和 `as_of`，禁止高置信结论 | `PARTIAL / STALE` | 刷新、接受限制或取消 |
| 无法确认责任人 | 不把任务发给猜测用户 | `BLOCKED: owner_unknown` | Sponsor 指定或授权目录来源 |
| 模型超时/无效输出 | 保留已提交领域结果并记录本次失败，不抹去已发生动作或伪造成功 | `AGENT_RUN_FAILED` | 重读领域状态与动作收据后有界恢复 |
| 人类任务过期 | 拒绝直接提交旧版本 | `EXPIRED` | 基于最新依赖重新签发 |
| 候选在批准后变化 | 使受影响批准失效 | `APPROVAL_INVALIDATED` | 重新审阅和批准 |
| 目标预检失败 | 不写入目标 | `RELEASE_BLOCKED` | 修复权限/格式/兼容性 |
| 发布请求成功但 readback 不符 | 不声称成功 | `RELEASE_FAILED` 或 `PARTIAL` | 重试、调查或回滚 |
| 多目标部分成功 | 保存逐目标结果 | `PARTIAL` | 由批准策略选择补发或回滚 |
| 回滚失败 | 停止自动动作并升级 | `ROLLBACK_FAILED / CRITICAL` | 人工 runbook 和系统 Owner |
| 结果指标缺失或口径改变 | 不报告改善 | `OBSERVATION_INCOMPLETE` | 修复测量或记录不可判定 |
| 竞品/客户系统不支持所需 API | 不伪装集成 | `INTEGRATION_BLOCKED` | 文件导入、人工步骤或重新评估试点 |

## 15. 产品验收指标

### 15.1 MVP 功能门

- 无旧 Contract 的电商高潜客户规范创建案例从目标到 Contract v1 与发布提案全程可重建；不要求先发布到外部目标；
- 每份批准契约有目标、Owner、范围、规则、映射、检查、样例/反例、证据、双时间、版本与明确批准；草案和模拟批准不能冒充真实企业批准；
- Agent 提出规范结构与候选规则，补证后自动恢复；图和列表展示真实领域状态，不用手工推进或预设动画代替执行；
- 可执行检查在自有样例与未见反例上复验，正确处理关联放大、缺失、时间、币种与零分母；不把文案相似度当作规范质量；
- 首轮另测创建/修订判别、基线绑定与历史保护，以及不同物理 Schema 和目标/例外变化；完整修订闭环后置，其状态保持 NOT RUN，不把保护测试记为 REVISION PASS；通过只限于已测范围，不宣称跨行业通用；
- 至少覆盖权限拒绝、陈旧证据、重复/过期回应、批准失效、无基线修订和关键事实不足；未授权外部动作与被标为完成却缺审计的批准次数必须为 0；
- fake model 工程回放、真实模型设计评估、人类 Browser 验收与客户结果分别记账；真实模型未运行时，其设计能力状态保持 NOT RUN；
- 后续沙箱独立验证单目标预览、授权、写入、readback、回滚及其失败状态；首轮不得声称这些能力通过；
- 人类产品 Browser 验收必须由用户明确记录 PASS，绑定精确 build/branch、数据与运行模式；静态图验收、自动化或 Agent 截图不能替代。

### 15.2 试点业务测量

以下用于真实团队试点。工程运行数据、角色扮演与模拟需求不得代填客户基线或业务结果；未接入发布目标时，下游指标记录未运行或不适用，不能记作成功。

| 指标 | 定义 | v0.1 判定方式 |
|---|---|---|
| Definition cycle time | 从有效 intake 到批准契约的日历时间 | 与客户同类历史或启动前基线比较；无基线不报改善 |
| Human handoffs | 需要人主动找到下一人的次数 | 区分 Agent 路由与人对人协调，不只统计消息数 |
| Rework rounds | 因信息/口径/映射遗漏导致返回前态的次数 | 记录原因，不把合理审议算作浪费 |
| Evidence completeness | 批准时必需证据、Owner、范围、时间和来源覆盖 | 按预先批准 checklist 计算，不由模型自行定分母 |
| Dispute resolution time | 从正式异议到解决/接受保留意见 | 按争议级别分层 |
| Downstream consistency | 获准目标实际读回的版本与契约一致度 | 逐目标 readback；不支持验证则不得计成功 |
| Adoption | 指定使用方在观察窗内引用新版本 | 来源和版本可追踪；访问不等于正确使用 |
| Rollback/release defects | 发布后需要回滚或修复的目标数与原因 | 零缺陷不是试点前提，但高风险未授权缺陷为阻断 |
| Outcome signal | 例如覆盖、转化、误触达或投诉变化 | 只报告观察与方法；无对照/设计时不作因果归因 |
| FDE non-reusable work | 试点中无法由产品或模板复用的人工小时 | 用于判断是否退化为定制项目 |

### 15.3 目标设定规则

- 真实试点的前两周优先建立基线，不预设“提升 30%”等无证据目标；自有 fixture 开发不以已有客户历史作为启动前提；
- 基线形成后，由客户与产品方共同批准量化目标和观察窗；
- 最小试点成功要求：完整跑通一个案例、无高严重度控制失效、相对基线至少一个协调/周期指标有可解释改善、客户明确愿意继续第二个案例；
- `FUNCTIONAL PASS` 仅指本版创建主场景的工程控制、真实 Agent 设计评估及对应 build 的人类 Web 验收均通过；只有 fake 回放通过时只能报告工程控制通过；无客户业务证据时另记 `PILOT OUTCOME PENDING`；
- 一个客户的结果不能直接外推到其他行业或部署模式。

### 15.4 阶段结果必须分开

以下是报告标签，不冻结产品公共状态枚举；精确验证包和执行授权见 §5.5、§18。

| 验证项 | 通过需要的证据 | 不可替代的结论 |
|---|---|---|
| 工程控制（Phase 0–1） | 确定性输入下的状态、等待恢复、权限、版本与审计检查 | 不证明真实模型设计能力或完整 MVP 功能通过 |
| 真实 Agent 设计（Phase 2） | 获授权的真实调用、输入记录、独立语义检查和未见反例 | 未调用保持 NOT RUN；不能复用 fake 结果 |
| 创建主场景功能（Phase 2 收口） | 工程控制 + 真实设计 + 对应 build 的人类 Web 验收 | 不证明完整修订、沙箱发布、预测效果或客户价值 |
| 完整修订闭环（后续独立范围） | 绑定旧版到候选差异、重新批准和新版本的完整验证 | 首轮只有保护测试时保持 NOT RUN |
| 沙箱发布（Phase 3） | 目标授权、实际写入、readback、回滚和失败检查 | 提案或导出不算已发布 |
| 客户结果（Phase 4） | 真实任务、主体、基线与观察证据 | 工程数据、角色扮演、公开订单不代填客户结果 |

## 16. MVP、后续与明确不做

| 范围 | v0.1 MVP | 后续候选 | 不做/需重开产品问题 |
|---|---|---|---|
| 场景 | 从零建立电商高潜客户识别规范，贯通指标/数据/业务规则；保留修订保护测试 | 完整已有规范修订、其他有证据的案例 | 任意问题通用 Agent、无证据的未来潜力预测 |
| 组织 | 一个专业用户启动的限定业务域；演示身份如实标注 | 真实 2–5 人试点、多域协作和模板 | 无 Owner 的全公司自动治理 |
| 来源 | 自有 fixture 的 3–4 类资料 | 独立授权的公开/真实只读来源与适配器 | 把候选来源当成已接入或默认传播第三方数据 |
| 协作 | Web 内受控任务与持久等待/恢复 | 一个实际通知渠道，再按证据扩展 | 以消息渠道或聊天记录作为状态源 |
| Agent | Mission 持续推进 + 有界 Agent Run；真实模型另批 | 有证据时引入角色化 Agent | 为展示而多 Agent，或把 fake 回放说成自主设计 |
| 定义 | 首份规范贯通指标、数据与职责规则；精确 Schema 待门 | 类型扩展与互操作规范 | 把所有企业知识塞入一个 Schema |
| 影响 | 自有样例、候选比较与只读校验 | 真实血缘、指标与获授权样本影响 | 伪造历史基线或未授权生产查询 |
| 发布 | 版本化提案；无外部写入 | 单目标沙箱通过后再讨论试点与多目标 | 一键全系统写入 |
| 观测 | 明确标注的 fixture 复审信号 | 获授权真实采用、异常与业务测量 | 用模拟信号宣称业务改善 |
| 部署 | 沿用全栈 TS 候选方向；不冻结基础设施 | SaaS/私有化按真实需求评审 | 由 PRD 写入推导依赖安装或部署授权 |

## 17. 现有 `semantic-agent` 复用地图

### 17.1 保留

| 现有能力 | 复用理由 | 新产品位置 |
|---|---|---|
| SourceConnector / SourceSnapshot | 来源、指纹和新鲜度是证据基础 | Evidence discovery adapter boundary |
| SourceBinding / registry / rollback | 显式映射、冲突和版本思路可复用 | Contract 到下游资产的受控 mapping；领域名称可能调整 |
| ContextPack lifecycle/import/export | 可移植、版本化上下文包有价值 | Case evidence/contract exchange 的输入，不直接等于批准契约 |
| deterministic ID/label/alias matching | 可解释确定性匹配优于模型暗箱 | 发现候选和去重，始终保持非权威 |
| AnalysisPlan DAG / preflight | 计划、依赖、预算、策略和新鲜度检查 | 影响模拟和只读证据任务 |
| QueryPlan AST / fixture compiler | 安全可测试的只读查询表达 | MVP impact fixture；不是产品核心查询引擎 |
| EvidenceEnvelope / ResultEnvelope | 显式覆盖、来源和部分失败 | Case evidence 和 simulation result |
| RuntimeHost / ControlledToolRegistry / LoopController | Agent 运行和工具权限的确定性边界 | ContextOx orchestration 内核候选 |
| TraceStore / SessionContext | correlation 和执行上下文基础 | 需持久化、企业身份和数据最小化扩展 |
| Pi adapter boundary | 隔离上游 Agent API | 保持薄适配和 fake stream contract tests |

### 17.2 需要修改或重新定位；方向确认不等于代码迁移授权

| 现有方向 | 问题 | 候选处理；未批准 |
|---|---|---|
| AlphaOx/分析 Agent 主叙事 | 入口仍容易被理解为 ChatBI | 对外产品改为数契/ContextOx；AlphaOx 保留历史工程追溯 |
| Binding 作为主要产品对象 | 技术映射不能承载完整业务变化 | 上移到 Definition Change Case + Contract；Binding 成为 mapping/release 子对象 |
| Session 是主要边界 | 规范工作跨人、跨天、跨系统 | Mission 持续推进，Case 保存业务事实与决策；Session 只是交互/执行上下文 |
| QueryPlan/SQL 路径 | 易把产品重新拉回问数 | 限定在证据与影响模拟，不做首要体验 |
| local-first 单用户 Web | 不能直接等同于跨主体、跨日 Mission 协作 | 作为原型或开发模式候选；真实身份、协作与生产部署需重新讨论 |
| in-memory/fixture store | 不能满足审计、恢复和多人一致性 | 定义持久化/并发/备份架构决策门 |

### 17.3 缺失能力；按阶段补齐

- 规范结构设计、候选比较、从零创建与已有规范修订的区分及验收；
- Mission 持续执行及 Case 状态机和领域事件；

## 18. 实施阶段候选

产品方向确认、文档写入、架构冻结、验证实施、依赖安装、真实模型/数据访问和发布分别授权。实施前在统一架构报告中补齐本场景、精确文件与依赖范围、身份/权限、状态/失败矩阵、数据新鲜度、维护责任、迁移/回滚、可观测性、清理与验收条件；当前报告和图的历史通过不能替代新案例验收。

### Phase 0：验证基线与持久执行试验（对应路径一）

- 确认模拟任务、自有数据范围、角色、固定时点和独立评估断言；明确可复用代码与不可作为输入答案的旧定义；
- 在独立实施门后，优先用最小测试模型、fake Pi 与隔离状态验证 DBOS 的重启恢复、等待前后信号、重复/乱序、并发 Worker、计时器、数据库部分失败、代码版本衔接及引擎退出；
- 动作结果未知时先对账，不承诺仅靠引擎实现外部 exactly-once；关键试验失败则带证据回到选型门，不默认另造调度平台；
- 客户访谈与需求验证继续进行，但不以尚未获得真实公司委托阻塞自有 fixture 的工程验证。

### Phase 1：自有 fixture 的最小持久闭环（对应路径二至三）

- 最小 Mission/Case/Task/Decision/Contract、持久状态和审计、统一自有验证包；
- 无旧 Contract 创建 → 规范候选 → 受控补证 → 有效回应自动恢复 → 明确裁决 → Contract v1 与提案；
- fake model 驱动确定性控制测试，最小调用界面读回实际状态与事件；不以完整 Web 为前置，也不计为真实模型设计质量验证；
- 创建主线、创建/修订判别、旧版绑定保护与关键失败路径分别检查；不要求完整修订闭环，不记 REVISION PASS。保留可执行检查与人工复核证据；完整 Web 验收在下一阶段进行，无外部发布。

### Phase 2：真实 Agent 设计能力与最小只读来源（对应路径三至四）

- 先独立批准模型、预算、数据路径和保留范围，再用同一自有资料验证真实设计、补证和重规划；
- 不向模型输入最终答案，以未见样例、不同 Schema、目标或例外变化检查适应能力；不能复用 fake 输出冒充真实调用；
- 公开数据、真实只读来源或实际协作渠道各自单独授权；缺权限或许可时保持阻塞，不扩大来源范围；
- 记录规范质量、控制失效、人工协调与调用成本；设计验证后完成真实状态投影的 Web 闭环和对应 build 的人类 Browser 验收，真实模型结果与工程回放分开记账。

### Phase 3：单目标沙箱发布（对应路径五）

- 一个明确获授权、可回滚的目标；实现并验证 compile/diff/validate/authorize/publish/verify/rollback/observe；
- 覆盖 readback 不符、结果未知、部分失败、批准失效和回滚失败；
- 模拟身份与业务数据不得冒充真实企业身份或生产运行。

### Phase 4：真实小团队试点（对应路径六）

- 使用真实任务、责任主体、最少获授权来源和基线；涉及发布时具备相应目标授权、审计和回滚 runbook；
- 分别记录功能、人类验收、客户结果与成本；无基线不报告效率提升或因果收益；
- 第二个案例验证复用是否增加、不可复用 FDE 人工量是否下降，再讨论规模化。

仓库/Pi 迁移与生产化仍按路径七单独审议；任何阶段通过都不自动授权下一阶段、提交、合并、发布或生产部署。

## 19. 依赖与风险

| 风险 | 影响 | 早期证伪/缓解 |
|---|---|---|
| 客户没有可用 Owner 或批准权 | Case 永久阻塞 | 试点准入条件；Sponsor 在启动前确认 RACI |
| 问题实际属于主数据或组织政治 | MVP 范围爆炸 | 选择边界清晰的单域案例；允许停止而非假装软件可解 |
| 竞品已有足够能力 | 独立产品价值不足 | 做正式 demo/RFP；比较总实施成本和真实流程 |
| Agent 微任务增加打扰 | 采用失败 | 测量任务数量、完成率和认知负担；提供批量/摘要/静默策略 |
| 集成成本吞噬价值 | 退化为 SI 项目 | 一个来源/目标开始；记录不可复用 FDE 工时 |
| 双时间和契约模型过重 | 业务用户难用 | UI 展示具体差异和生效语义；Schema 复杂性留在系统内部 |
| 敏感数据进入模型/日志 | 合规和信任失败 | 引用优先、字段最小化、私有部署/provider 政策决策门 |
| 模型/工具误判 Owner 或影响 | 错误路由和发布 | 候选而非事实；来源、人工确认、服务端策略和 fail closed |
| 结果信号被误作因果 | 错误产品与业务决策 | 预先测量计划、混杂因素、对照/分析能力边界 |
| Pi 或其他上游变化 | 运行时回归、供应链风险 | 薄适配、锁版、契约测试、独立上游同步流程和回滚 |
| 把模拟需求或角色当成客户证据 | 错误判断产品需求与可销售性 | 明确来源与运行模式，真实任务、Owner 与基线另验 |
| 旧定义或验收答案泄漏到 Agent 输入 | 误把复述当成从零设计 | 输入与评估端隔离，记录模型实际可见上下文，使用变化与未见反例 |
| 公开数据用途或许可未确认 | 无法安全下载、传播或对外演示 | 自有 fixture 优先，按具体版本和用途独立核验，不默认使用第三方数据 |
